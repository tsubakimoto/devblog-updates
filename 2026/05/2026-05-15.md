## Advanced Shader Delivery expands Public Preview with AMD

- **Blog:** Directx
- **URL:** https://devblogs.microsoft.com/directx/advanced-shader-delivery-expands-public-preview-with-amd

### 要約
Advanced Shader Delivery (ASD) が、ROG Xbox Ally 以外の Windows 11 PC にも広がり、AMD の discrete GPU とゲーム向けノート PC の integrated GPU で Public Preview として利用できるようになりました。ASD はダウンロード時に事前コンパイル済みシェーダーを届けることで、初回起動時の長いロード時間と shader stutter を減らす仕組みです。記事では、Forza Horizon 6 が ASD の効果を示すタイトルとして紹介されています。利用には Windows 11 24H2 以降や最新の Gaming Services、Xbox Insider Hub、対応 GPU/ドライバーが必要です。ゲーム開発者向けには、AgilitySDK と Xbox Partner Center の state object database (SODB) を使った対応方法が案内されています。

### 開発者にとって重要なこと
PC ゲームのロード時間、初回体験、shader compilation に課題があるチームに直接関係します。特に AMD 対応 Windows 11 環境を持つタイトルでは、配布後の体験改善やサポート対象デバイスの整理が必要になります。ゲーム配信やビルドパイプライン側で、事前コンパイル資産の扱いを確認するきっかけになります。

### アクションプラン
- ⚠️ 影響対象のタイトルがある場合は、ASD の対応可否と必要条件を確認する。
- Xbox PC app や対象 GPU での起動時間・stutter の改善余地を実機で検証する。
- 対応するなら、AgilitySDK と SODB の導入手順を確認し、Partner Center への登録手順を整理する。

## The case of the <CODE>Create­File­Mapping</CODE> that always reported <CODE>ERROR_<WBR>ALREADY_<WBR>EXISTS</CODE>

- **Blog:** Oldnewthing
- **URL:** https://devblogs.microsoft.com/oldnewthing/20260515-00/?p=112327

### 要約
Named file mapping を作成しているのに、サイズが意図より小さくなり、`GetLastError()` で `ERROR_ALREADY_EXISTS` が返る事例を扱っています。原因は、同じ名前の kernel object を別ソフトウェアがすでに使っていたことでした。記事では Process Explorer を使って既存ハンドルを確認し、webcam companion software が同名を使っていたことが分かった流れが説明されています。対策として、file mapping 名に GUID を付けて衝突を避けています。最後に、意図しない名前衝突と意図的な攻撃は別問題だと補足しています。

### 開発者にとって重要なこと
Windows の名前付き kernel object を使うアプリやライブラリ全般に関係します。ローカル環境で再現しにくいバグや、起動直後なのに既存扱いになる問題の切り分けに役立ちます。共有リソース名はユニーク性を前提に設計する必要があります。

### アクションプラン
- 名前付き object を使う実装があるなら、衝突しにくい命名規則に見直す。
- `CreateFileMapping` / `CreateMutex` などで `ERROR_ALREADY_EXISTS` が出る経路をログに残す。
- ⚠️ 他プロセスとの衝突が許されないなら、GUID などで一意化する。

## The Coding Harness Behind GitHub Copilot in VS Code

- **Blog:** VS Code Blog
- **URL:** https://devblogs.microsoft.com/vscode-blog/the-coding-harness-behind-github-copilot-in-vs-code

### 要約
GitHub Copilot in VS Code の周辺にある coding harness が、モデル、ツール、agents、providers の進化に伴ってなぜ重要かを解説する記事です。Copilot の体験は単にモデル本体だけでなく、実行やツール連携を支える枠組みによって成立していることを示しています。詳細は本文参照ですが、AI 支援コーディング機能の土台側に焦点がある更新です。VS Code 内の Copilot 利用や、同種の拡張機能設計を考える上で参考になります。

### 開発者にとって重要なこと
VS Code で Copilot を利用している開発者だけでなく、AI エージェントや拡張機能を設計するチームにも関係します。モデル変更だけではなく、周辺の harness が使い勝手や安定性を左右する点を再確認できます。Copilot の導入・運用をしている組織は、機能の土台がどう変わるかを追う必要があります。

### アクションプラン
- VS Code で Copilot を使っているなら、現在のワークフローへの影響を確認する。
- AI 拡張やエージェント連携を作っている場合は、本文を読み、harness 層の前提を見直す。
- 既存の provider / tool integration があるなら、今後の変更に備えて互換性を点検する。
