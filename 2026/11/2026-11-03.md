## GitHub Copilot is now a default agent in JetBrains Air

- **Blog:** Java
- **Author:** Hang Wang
- **URL:** https://devblogs.microsoft.com/java/github-copilot-jetbrains-air

### 要約
GitHub Copilot が JetBrains Air の標準エージェントとして利用可能になり、既存の Copilot サブスクリプションで IDE 内からコーディング作業を委任し、並列セッションを管理して変更を確認できます。Air のローカル実行に加えて Cloud Run にも対応し、JetBrains IDE 2026.2.4 以降では Next Edit Suggestions のプロバイダーとしても選択できます。

### 開発者にとって重要なこと
JetBrains IDE でのエージェント利用の選択肢が増えます。Air は手軽なエージェント操作向けで、インラインチャットやコード補完、エンタープライズ管理などを含む完全な統合には既存の Copilot プラグインが引き続き推奨されています。

### アクションプラン
- JetBrains Air を使う開発者は、既存の Copilot サブスクリプションで GitHub Copilot エージェントを選択し、ローカルまたは Cloud Run の作業フローを試す。
- IDE 2026.2.4 以降では、必要に応じて Settings → Editor → General → Code Completion → Inline から Copilot の Next Edit Suggestions を有効にする。
- 組織の管理機能やプラグイン固有機能が必要な場合は、Air と Copilot プラグインの機能差を確認して選択する。

### リファレンス
- [GitHub Copilot is now a default agent in JetBrains Air](https://devblogs.microsoft.com/java/github-copilot-jetbrains-air)

## My Favorite Undocumented Feature in SQL MCP Server

- **Blog:** Azure SQL
- **Author:** Jerry Nixon
- **URL:** https://devblogs.microsoft.com/azure-sql/sql-mcp-server-hidden-feature-default-configuration

### 要約
Data API builder 2.0 以降のコンテナーイメージには、全スキーマのテーブルを自動公開する基本設定が含まれ、`DAB_CONNSTRING` 環境変数で接続文字列を指定すれば独自の設定ファイルなしで SQL MCP Server を起動できます。この方法はローカルや Azure 上の概念実証を素早く始めるのに便利ですが、既定設定は開発用です。

### 開発者にとって重要なこと
設定準備の手間を減らせる一方、基本設定では開発環境向けのホスト設定や匿名アクセス可能な CRUD 権限が有効になる場合があります。データベース側のセキュリティは維持されますが、エンドポイントをそのまま本番公開する構成ではありません。

### アクションプラン
- ローカルの概念実証では `DAB_CONNSTRING` を使い、接続文字列を設定ファイルに直接記載せず MCP エンドポイントを試す。
- ⚠️ 本番投入前に、匿名アクセス、CRUD 権限、Swagger/Nitro、ヘルスエンドポイント、シークレット管理を明示的に見直し、開発用の既定設定をそのまま公開しない。
- Azure Container Apps、ACI、AKS への展開時も、環境変数の保護とネットワーク・認証・データ権限の構成を確認する。

### リファレンス
- [My Favorite Undocumented Feature in SQL MCP Server](https://devblogs.microsoft.com/azure-sql/sql-mcp-server-hidden-feature-default-configuration)

## Modernize MongoDB applications with Azure DocumentDB: From assessment to what’s next

- **Blog:** DocumentDB
- **Author:** Marko Hotti
- **URL:** https://devblogs.microsoft.com/documentdb/modernize-mongodb-applications-with-azure-documentdb-from-assessment-to-whats-next

### 要約
Azure DocumentDB への MongoDB アプリケーション移行では、データを移す前に互換性を評価し、Azure Migrate と VS Code の Azure DocumentDB Migration Extension で移行候補や非互換箇所を把握する流れを紹介しています。移行は DMS を利用したオフライン／オンライン方式を選べ、データ・クエリ・インデックス・性能を検証してから本番切り替えを行うことが推奨されています。

### 開発者にとって重要なこと
MongoDB 互換 API やドライバーが使えても、アプリが依存するコマンドや集約パイプライン、インデックスの互換性は個別に確認が必要です。オンライン移行では変更ストリームや oplog 容量、TTL インデックスの扱いが切り替え計画に影響します。

### アクションプラン
- 移行候補を棚卸しし、Azure Migrate の評価と Migration Extension の機能・クエリ互換性分析で懸念点を特定する。
- ダウンタイム要件に合わせてオフライン／オンライン移行を選び、オンライン方式では変更ストリーム、oplog 容量、最終切り替え手順を事前に検証する。
- リハーサル移行で件数・代表データ・インデックス・重要クエリ・性能を確認し、TTL インデックスは移行前後の扱いを計画する。
- まず既存機能の移行と検証を完了し、ベクトル検索や AI 機能の追加は別フェーズとして評価する。

### リファレンス

## Delivering Skills in NuGet packages

- **Blog:** .NET
- **Author:** Richard Lander
- **URL:** https://devblogs.microsoft.com/dotnet/delivering-skills-in-nuget-packages

### 要約
NuGet パッケージに Agent Skills 形式の `SKILL.md` を同梱し、パッケージの API や使い方に合った指示をエージェントへ提供する取り組みを紹介しています。復元済みパッケージ内のスキルを `dotnet-inspect` で確認したり、`dotnet-package-skills` でリポジトリの `.agents/skills` に取り込んだりする方法が示されています。

### 開発者にとって重要なこと
パッケージに同梱されたスキルは、そのパッケージ固有の知識や推奨手順をエージェントに渡し、README やメタデータからの推測を減らす可能性があります。利用者側では、依存パッケージが持つスキルの内容とリポジトリへの取り込み方を把握する必要があります。

### アクションプラン
- .NET プロジェクトで `dotnet-inspect project <project-file> -S Skills` を使い、依存パッケージにスキルが含まれているか確認する。
- チームで採用する場合は、`dotnet-package-skills` による `.agents/skills` へのコピーを試し、更新・レビューの運用を決める。
- パッケージ作成者は、配布するスキルが正確で保守可能かを確認し、通常のパッケージ文書と区別できるようにする。

### リファレンス
- [Delivering Skills in NuGet packages](https://devblogs.microsoft.com/dotnet/delivering-skills-in-nuget-packages)

## Sparse Package

- **Blog:** Inside MSIX
- **Author:** Howard Kapustein
- **URL:** https://devblogs.microsoft.com/insidemsix/sparse-package

### 要約
Sparse package は `AppxManifest.xml` などのフットプリントファイルを含み、実行ファイルなどのペイロードを含まない MSIX パッケージとして作成できます。外部インストーラーで配置したファイルを External Location と組み合わせて参照する仕組みを、マニフェスト例や `makeappx.exe` の `/nv` オプションを使って説明しています。

### 開発者にとって重要なこと
既存のインストーラーで配布するアプリにパッケージ ID やマニフェスト機能を加えつつ、MSIX 内の重複ペイロードを省ける可能性があります。パッケージは外部コンテンツを前提とするため、External Location の要件や署名・インストール方法を合わせて設計する必要があります。

### アクションプラン
- MSIX でアプリの登録情報を提供しつつペイロードを別途配布する必要がある場合、External Location と sparse package の適合性を確認する。
- 検証用パッケージではマニフェストの外部コンテンツ宣言、署名、参照ファイルの配置をテストし、通常の MSIX と異なるインストール要件を確認する。
- パッケージを小さくする目的だけで採用せず、Windows の外部コンテンツの仕様とアプリの更新・アンインストール手順を確認する。

### リファレンス
- [Sparse Package](https://devblogs.microsoft.com/insidemsix/sparse-package)

## Your app needs documents. Do you really want to build a document platform?

- **Blog:** Microsoft 365 Developer
- **Author:** Steve Pucelik
- **URL:** https://devblogs.microsoft.com/microsoft365dev/your-app-needs-documents-do-you-really-want-to-build-a-document-platform

### 要約
文書機能を自作すると、ファイル管理に加えて権限、共同編集、検索、監査、保持、データ損失防止などの基盤運用まで必要になると説明しています。SharePoint Embedded を利用すれば、アプリの UI と業務ロジックを独自に構築しながら、顧客の Microsoft 365 テナント内で文書管理・共同作業・ガバナンス機能を利用できます。

### 開発者にとって重要なこと
文書管理が製品の差別化要素でない SaaS や業務アプリでは、SharePoint Embedded が独自の文書基盤を構築・運用する代替案になり得ます。テナント境界、Microsoft 365 のライセンスや設定、アプリとテナントの構成が要件に合うか事前評価が必要です。

### アクションプラン
- 文書機能の要件を保存・権限・共同編集・検索・コンプライアンス・運用に分解し、自社実装と SharePoint Embedded の責任範囲を比較する。
- 顧客テナント内のデータ配置、ガバナンス、ライセンス、マルチテナント構成を設計段階で確認する。
- 適合性を検証する場合は、SharePoint Embedded の VS Code 拡張またはプレビューの MCP Server と公式ドキュメントを使い、小規模な試作を行う。
