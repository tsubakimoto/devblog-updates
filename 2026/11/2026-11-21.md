## Hosted agents in your own virtual network: five checks when the Agents page times out

- **Blog:** Foundry
- **Author:** Muzz Imam
- **URL:** https://devblogs.microsoft.com/foundry/hosted-agents-private-network-setup

### 要約
Microsoft Foundry の Hosted Agents を独自 VNet で利用する際に、Agents ページがタイムアウトする場合の確認点を、エージェント用サブネット、Cosmos DB などのプライベート DNS、Microsoft Entra ID への通信、ピアリング済み VNet の経路と DNS、削除済みアカウントによるサブネット占有の5項目で解説しています。特に、Entra ID の TLS 検査除外、エージェント VNet からプライベート DNS ゾーンを解決できること、アカウント削除後にサブネットがすぐ解放されるとは限らないことを説明しています。

### 開発者にとって重要なこと
Foundry Hosted Agents を BYO VNet で運用するチームでは、タイムアウトの原因がエージェント自体ではなく、名前解決、ファイアウォール、ルート、サブネット設定にある場合があります。ネットワーク挿入は Foundry アカウントの作成時に設定する必要があり、既存アカウントには後から追加できません。また、ソフト削除アカウントのパージは取り消せないため、開発・テスト環境でも削除手順に注意が必要です。

### アクションプラン
- Foundry 管理者は `az cognitiveservices account show` でエージェント用サブネットを特定し、委任先が `Microsoft.App/environments` であること、サイズが `/27` 以上（本番では `/24` 以上を推奨）、VNet 範囲の重複がないことを確認する。新規アカウントではネットワーク挿入を作成時に構成する。
- Agents ページのタイムアウト時は Cosmos DB のプライベートエンドポイントと `privatelink.documents.azure.com` の DNS ゾーン・レコード・VNet リンクを確認する。Key Vault、Storage、AI Search なども、エージェントサブネットから名前解決と接続ができるか検証する。
- ファイアウォールで TLS 検査を行う場合は、`login.microsoftonline.com`、`{region}.login.microsoft.com`、`control-{region}.identity.azure.net` と必要なマネージド ID の通信を許可し、Entra ID 通信を TLS 検査から除外する。NSG を使う場合も必要なアウトバウンド通信を許可する。
- ピアリング先のプライベートエンドポイントへ通信する場合は、エージェント VNet 側から DNS が解決できること、ユーザー定義ルートが必要な経路を妨げないことを確認する。サブネット再利用時に `DelegatedSubnetInUse` が出た場合は、旧アカウントがソフト削除状態か調べる。パージは永久削除となるため、対象を確認してから実行する。
