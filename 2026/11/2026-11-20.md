## How to Chunk Documents in Azure SQL Database for RAG

- **Blog:** Azure SQL
- **Author:** Dhruv Malik
- **URL:** https://devblogs.microsoft.com/azure-sql/how-to-chunk-documents-in-azure-sql-database-for-rag

### 要約
Azure SQL Database の `AI_GENERATE_CHUNKS` で文書を固定文字数に分割し、Azure OpenAI で生成した埋め込みを `VECTOR` 列に保存して、`VECTOR_DISTANCE` や `VECTOR_SEARCH` で検索する RAG の検索部分を紹介しています。チャンクのオーバーラップ率の比較方法や、互換性レベル 170 以上などの要件も説明しています。例は検索の基礎であり、チャットボット全体や本番対応を保証するものではありません。

### 開発者にとって重要なこと
文書を Azure SQL Database に保管しているチームは、別のベクトルストアを導入せずに検索拡張生成の検索部分を試せます。一方、チャンクサイズは文字数単位で文書構造を考慮せず、埋め込み生成には外部 Azure OpenAI エンドポイントの利用料やデータ取り扱いの検討が必要です。

### アクションプラン
- Azure SQL Database で試す場合は、テスト用データベースで互換性レベル、エンドポイント接続、モデルとベクトルの次元数を確認する。既存環境の互換性レベルを変更する場合は、影響を検証して承認を得る。
- 代表的な文書と質問を使い、チャンクサイズやオーバーラップ率を変えて検索結果を評価する。固定境界による文脈の分断、重複チャンク、埋め込み費用、検索品質を確認し、例示値をそのまま本番設定にしない。
- 文書を外部モデルへ送信してよいか確認し、資格情報はソースコードに置かず、承認済みのシークレット管理方法で設定する。小規模データではベクトルインデックスの作成要件（非 NULL ベクトル 100 件以上）も確認する。

## Copilot Code Reviews for Azure Repos is generally available

- **Blog:** DevOps
- **Author:** Dan Hellem
- **URL:** https://devblogs.microsoft.com/devops/copilot-code-reviews-for-azure-repos-is-generally-available

### 要約
Azure Repos 向け Copilot Code Review が一般提供になりました。組織・プロジェクト・リポジトリ単位の有効化やカスタム指示、レビューの労力レベル、自動レビューに対応し、指摘コメントや適用可能な修正候補をプルリクエストに提示します。利用量に応じた課金で、Azure サブスクリプションに請求されます。

### 開発者にとって重要なこと
Azure DevOps 上のプルリクエストに AI レビューを組み込めますが、Copilot は承認やマージのブロックを行わず、最終的なレビュー責任はチームに残ります。レビュー量や PR の大きさで費用が変わるため、全リポジトリへの展開前にコストと運用を確認する必要があります。

### アクションプラン
- Azure DevOps の組織管理者は **Organization settings > Repos > Repositories** で有効化範囲を決め、監査ログに設定変更が記録されることを確認する。
- まず 1〜2 個のリポジトリで試し、組織・プロジェクト・リポジトリのカスタム指示と Lite / Balanced の労力レベルをチームの基準に合わせる。自動レビューを使う場合は対象ブランチのポリシーを確認する。
- Azure Cost Management の使用量を監視し、必要に応じてプロジェクト別の予算アラートを設定する。AI の指摘を人間のレビューや承認の代替にしない。

### リファレンス
- [Copilot Code Reviews for Azure Repos is generally available](https://devblogs.microsoft.com/devops/copilot-code-reviews-for-azure-repos-is-generally-available)

## AI is Changing the Cross-Platform Decision Matrix

- **Blog:** .NET
- **Author:** David Ortinau
- **URL:** https://devblogs.microsoft.com/dotnet/ai-cross-platform-decision-matrix

### 要約
.NET MAUI アプリを .NET for iOS と .NET for Android の個別 UI に置き換えた実験を通じ、AI エージェントがクロスプラットフォーム開発の選択に与える影響を検討しています。実験では個別 UI の初回構築は短期間で進み、特定の実行時構成で起動時間やアプリサイズが改善しましたが、同じ機能の実装・検証にはより多くの作業がかかり、調整役エージェントの時間も大きくなりました。結果は単一アプリと限られた端末・構成での測定であり、一般的な優劣を示すものではありません。

### 開発者にとって重要なこと
エージェントはプラットフォーム固有 UI の初期実装コストを下げても、各 OS でのテスト、端末検証、バグ対応、レビューの負担まではなくしません。.NET MAUI、Blazor Hybrid、描画 UI、ネイティブ UI の選択では、チームが所有・検証できるプラットフォーム数と、実測した性能・サイズ要件を考慮する必要があります。

### アクションプラン
- .NET チームは既存アプリの実際のユーザージャーニーで、起動時間・画面遷移・パッケージサイズなどの問題を測定してから、個別 UI 化を検討する。
- 移行を試す場合は、重要な画面を一つ選び、初回ポートだけでなく次の機能追加にかかる実装・テスト・調整コストも比較する。
- 個別 UI を採用する場合は、各プラットフォームの端末検証、テスト、レビューを担う人員とエージェントの能力を計画する。記事の数値を別アプリや構成にそのまま当てはめない。

### リファレンス
- [AI is Changing the Cross-Platform Decision Matrix](https://devblogs.microsoft.com/dotnet/ai-cross-platform-decision-matrix)

## Embracing MLIR in Windows ML: Windows-native inferencing built on DX CGC

- **Blog:** Foundry On Windows
- **Author:** Anastasiya Tarnouskaya, Tucker Burns, Vicente Rivera
- **URL:** https://devblogs.microsoft.com/foundry-on-windows/winml-cgc

### 要約
Windows ML 2.9.42 Experimental で、MLIR ベースの DirectX Compute Graph Compiler（DX CGC）を使う Windows ネイティブ推論経路の初期サポートが発表されました。実験的な Runtime API と Task API は ONNX に加えて一部シナリオで GGUF や SafeTensors を扱い、既存の ONNX Runtime アプリ向けには Compute Graph Execution Provider も用意されています。今回の CGC GPU 向けベンダー固有アクセラレーションは対応ハードウェアが限定され、対応範囲は今後拡大予定です。

### 開発者にとって重要なこと
Windows アプリでローカル推論を行う開発者は、対応ハードウェア上で GPU 推論を評価したり、モデルを一度 CGIR に変換して複数ベンダーのハードウェアを対象にする経路を試したりできます。API、コンパイラー、推論エンジンは初期段階の実験版なので、本番運用中の既存 ONNX Runtime 経路とは成熟度を分けて判断する必要があります。

### アクションプラン
- Windows ML を評価する場合は用途に応じて Runtime API、Task API、既存 ONNX Runtime 向け CG EP を選び、実験版 API の変更可能性を考慮して隔離した検証環境で試す。
- NVIDIA GPU のベンダー固有アクセラレーションを試す場合は、記事記載の GeForce 621.24 以降の対応ドライバーとモデル要件を確認する。ほかの GPU や CPU / NPU では実行経路と加速条件が異なる点に注意する。
- Windows ML CLI とサンプルでモデル変換・ベンチマークを行い、対象デバイスでの品質・性能を確認する。実験結果や問題は Windows ML GitHub で共有する。

### リファレンス
- [Embracing MLIR in Windows ML: Windows-native inferencing built on DX CGC](https://devblogs.microsoft.com/foundry-on-windows/winml-cgc)

## Serve open models in production with Foundry Managed Compute

- **Blog:** Foundry
- **Author:** Manoj Bableshwar
- **URL:** https://devblogs.microsoft.com/foundry/managed-compute-ga

### 要約
Microsoft Foundry Managed Compute が一般提供となり、専用 GPU 上で 150 以上のオープンモデルを運用できるようになりました。モデルに応じて NVIDIA A100 / H100 / H200 や AMD MI300X を選び、Global、米国または EU Data Zone のデプロイを構成できます。インスタンス数によるスケール、監視、プロンプトキャッシュなどの運用方法と、LoRA アダプターのプレビュー機能も紹介しています。

### 開発者にとって重要なこと
自前でサービング用コンテナーや GPU 基盤を運用せずにオープンモデルを提供できる一方、GPU インスタンスは時間単位で課金され、デプロイにはクォータと適切な Foundry 権限が必要です。性能やスループットはモデル、GPU、テンプレート、負荷によって異なるため、実際のワークロードで容量と費用を見積もる必要があります。

### アクションプラン
- Foundry を利用するチームはモデルカタログで Managed Compute 対応モデルとデプロイテンプレートを確認し、リージョン、データゾーン、GPU、コンテキスト長が要件に合うか検討する。
- 検証時は小さなインスタンス数から始め、デプロイ画面の時間単価と GPU クォータを確認したうえで、代表的な負荷によるスループット、HTTP 429、ストリーミング遅延を Azure Monitor で測る。
- 本番展開前にモデルライセンス、入力データの取り扱い、認証、費用上限を確認し、負荷に応じたインスタンス数やプロンプトキャッシュの効果を評価する。

### リファレンス
- [Serve open models in production with Foundry Managed Compute](https://devblogs.microsoft.com/foundry/managed-compute-ga)

## Another failed attempt to get the icon for the icon for the .. parent folder

- **Blog:** Oldnewthing
- **Author:** Raymond Chen
- **URL:** https://devblogs.microsoft.com/oldnewthing/20261120-00/?p=112883

### 要約
Windows Shell の `SHGetFileInfo` に `C:\dir\..` を渡しても親フォルダーのアイコンを取得できない理由を解説しています。Shell namespace は各フォルダーが子項目を独自に解析するツリーであり、`..` を「親へ戻る」構文として扱う保証はありません。`.` や `..` を解決したファイルシステムパスが必要なら、`GetFullPathName` や `PathAllocCombine` などを使う方法を示しています。

### 開発者にとって重要なこと
Shell API のパス文字列は通常のファイルシステムパス処理と同じとは限らず、Shell namespace 項目を単純な文字列の正規化で扱うと解析に失敗する場合があります。ファイルパスの解決と Shell 項目の識別を区別することが重要です。

### アクションプラン
- Windows Shell API に渡す前に親フォルダーを特定する必要がある場合は、文字列へ `..` を追加せず、必要に応じて `GetFullPathName` または `PathAllocCombine` でファイルシステムパスを解決する。
- 仮想フォルダーなど Shell namespace の項目を扱うコードでは、ファイルシステムのパス規則を前提とせず、各項目の解析・親子関係を Shell の API で処理する。
