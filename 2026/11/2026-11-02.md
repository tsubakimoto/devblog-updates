## My Team Is Growing, How Do I Structure Who Gets Access to What?

- **Blog:** Cosmosdb
- **Author:** Iria Osara
- **URL:** https://devblogs.microsoft.com/cosmosdb/azure-cosmos-db-access-control-growing-teams

### 要約
Azure Cosmos DB for NoSQL のアクセス管理を、個人単位ではなく役割に基づいて構成する方法を解説しています。リソース管理のコントロールプレーンとデータ操作のデータプレーンを分離し、Microsoft Entra グループやワークロードごとのマネージド ID に、必要最小限のロール・スコープ・期間で権限を付与することを推奨しています。

### 開発者にとって重要なこと
チームやアプリケーションが増える環境では、広すぎる権限や恒久的な本番アクセスを避けつつ、開発・運用・分析それぞれに必要なアクセスを設計できます。アカウントキー認証は細かく設定したデータ権限を迂回しうるため、Entra 認証への移行状況もアクセス設計の一部です。

### アクションプラン
- Cosmos DB の各ユーザー・アプリ・自動化 ID が担う役割と、コントロールプレーン／データプレーンのどちらを使うかを棚卸しする。
- グループと個別のマネージド ID に適切な組み込みロールを割り当て、可能な限りデータベース／コンテナー単位にスコープを絞る。書き込み専用など組み込みロールで過剰な権限になる場合はカスタムロールを検討する。
- 本番環境の昇格アクセスは期限付きにし、キー認証から移行する場合は依存先を検証してからキーをローテーションし、ローカル認証を無効化する。

### リファレンス
- [My Team Is Growing, How Do I Structure Who Gets Access to What?](https://devblogs.microsoft.com/cosmosdb/azure-cosmos-db-access-control-growing-teams)

## How Microsoft SQL learned to recover without undoing everything first

- **Blog:** Azure SQL
- **Author:** Anna Hoffman
- **URL:** https://devblogs.microsoft.com/azure-sql/your-server-wasnt-slow-it-was-waiting-we-fixed-it-with-constant-time-recovery

### 要約
Azure SQL の Constant Time Recovery (CTR) が、Persistent Version Store と論理的な取り消しを利用して、障害後に巨大な未コミットトランザクションを行単位で巻き戻す必要をなくす仕組みを説明しています。記事では、Azure SQL Database での復旧時間の長いテールが短縮した実績を紹介し、この仕組みが現在の Accelerated Database Recovery (ADR) として提供されていること、ログ使用量やロールバックにも利点があることを解説しています。

### 開発者にとって重要なこと
Azure SQL Database では ADR が常時有効で、SQL Server では 2019 以降で利用できますが、既定では無効です。SQL Server の大規模トランザクション、ロールバック時間、トランザクションログ容量や復旧時間を見直す際に関係します。ADR の有効化は性能特性にも影響しうるため、記事の数値だけで本番環境への適用を判断せず、自環境のワークロードで評価する必要があります。

### アクションプラン
- Azure SQL Database を利用している場合は、ADR が有効である前提で、障害復旧や大規模ロールバックの設計を確認する。
- SQL Server を運用している場合は、バージョンと ADR の設定を確認し、導入を検討するならテスト環境で代表的なトランザクションの性能・ログ使用量・バージョンストアのクリーンアップを評価する。
- 実装背景や測定条件を確認する場合は、記事からリンクされている論文と ADR の公式ドキュメントを参照する。

### リファレンス
- [How Microsoft SQL learned to recover without undoing everything first](https://devblogs.microsoft.com/azure-sql/your-server-wasnt-slow-it-was-waiting-we-fixed-it-with-constant-time-recovery)
