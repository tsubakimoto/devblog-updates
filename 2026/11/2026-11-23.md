## More deployment choice for open-source DocumentDB with Azure Arc and Azure Local

- **Blog:** Documentdb
- **Author:** Theo van Kraay
- **URL:** https://devblogs.microsoft.com/documentdb/documentdb-azure-arc-azure-local

### 要約
オープンソースの DocumentDB を、Azure Arc 対応 Kubernetes や Azure Local など、顧客が管理する環境で評価するプレビューが紹介されました。MongoDB API 互換のゲートウェイ、PostgreSQL によるストレージに加え、クラスター内の HA、監視、バックアップ／復元などを試せます。

### 開発者にとって重要なこと
既存アプリの近くやエッジ、ハイブリッド環境でドキュメントデータベースを検証できます。一方、インフラとデータベースの運用責任は利用者側にあり、プレビュー中は Microsoft のサポート対象外で、本番利用は禁止されています。機能・環境の制約や Azure への接続依存も事前確認が必要です。

### アクションプラン
- Kubernetes 上の DocumentDB を検討する場合は、まずアプリの代表的なワークフローと評価項目を決め、プレビューの範囲・制限を確認する。
- 合成データを使い、使い捨ての Kind 環境と公式クイックスタートで接続、クエリ、バックアップなどを評価する。
- ⚠️ 本番データや本番ワークロードには使用しない。Azure Arc、Azure Local、Kubernetes を含む環境互換性や運用要件を個別に検証する。

### リファレンス
- [More deployment choice for open-source DocumentDB with Azure Arc and Azure Local](https://devblogs.microsoft.com/documentdb/documentdb-azure-arc-azure-local)

## Agentic Autofix for GitHub Advanced Security for Azure DevOps is in public preview

- **Blog:** DevOps
- **Author:** Laura Jiang
- **URL:** https://devblogs.microsoft.com/devops/agentic-autofix-for-advanced-security-for-azure-devops-public-preview

### 要約
GitHub Advanced Security for Azure DevOps 向け Agentic Autofix がパブリックプレビューになりました。CodeQL／サードパーティ SARIF のコードスキャン警告や依存関係の脆弱性警告に対し、リポジトリを調査して複数ファイルの変更案を作成し、レビュー用プルリクエストを開きます。修正生成の利用料は Azure サブスクリプションに請求されます。

### 開発者にとって重要なこと
修正案は既存の Azure Pipelines／プルリクエストの流れでレビューできますが、自動マージはされず、警告が常に修正できるわけでもありません。生成にはトークン消費に応じた費用が発生するため、セキュリティ担当者と Azure DevOps 管理者は利用範囲と予算を調整する必要があります。

### アクションプラン
- Azure DevOps の組織、プロジェクト、またはリポジトリ設定で Autofix を有効化し、対象となるコードスキャン／依存関係アラートを選んで試す。
- `.github/copilot-instructions.md` などに規約やテスト手順を記述し、チームの修正基準をエージェントに伝える。
- ⚠️ 生成された差分を必ずレビューし、通常のビルド・テストを実施してからマージする。マージ後にスキャナーを再実行して警告の解消を確認する。
- Azure Cost Management で AI Credit for AzDO GAC の使用量を確認し、必要に応じて組織／プロジェクト別の予算アラートを設定する。

### リファレンス
- [Agentic Autofix for GitHub Advanced Security for Azure DevOps is in public preview](https://devblogs.microsoft.com/devops/agentic-autofix-for-advanced-security-for-azure-devops-public-preview)

## Run local models in your .NET apps with Llama on Windows

- **Blog:** .NET
- **Author:** Luis Quintanilla
- **URL:** https://devblogs.microsoft.com/dotnet/local-models-dotnet-llama-windows

### 要約
Windows 11 のトレイアプリ「Llama on Windows」を使い、PC 上でオープンモデルをダウンロード・実行し、.NET アプリから呼び出す方法が紹介されました。Llama はローカルで llama.cpp サーバーを起動し、OpenAI 形式の API を `http://localhost:9931` で提供します。.NET 11 のサンプルでは `Microsoft.Extensions.AI` の `IChatClient` を介したチャットやツール呼び出しを実装しています。

### 開発者にとって重要なこと
プロンプトや応答を PC 内に保ったまま、オフライン環境でも推論を試せます。OpenAI 互換エンドポイントを利用するため、既存の .NET AI コードとの接続を共通インターフェースに寄せられますが、実行可能なモデルやツール呼び出しは PC のハードウェアとモデルの対応状況に依存します。

### アクションプラン
- Windows 11 環境で Llama を導入し、ハードウェアに合うモデルを選んでローカル推論を試す。
- .NET 11 SDK と公式サンプルを使い、`IChatClient` 経由のチャットやストリーミング、対応モデルでのツール呼び出しを検証する。
- 実運用前に、利用モデルのツール対応、必要なメモリ／コンテキスト長、組織のデータ取り扱い要件を確認する。

### リファレンス
- [Run local models in your .NET apps with Llama on Windows](https://devblogs.microsoft.com/dotnet/local-models-dotnet-llama-windows)

## New guidance to optimize Git performance in Azure Repos

- **Blog:** DevOps
- **Author:** Artur Karachev
- **URL:** https://devblogs.microsoft.com/devops/new-guidance-to-optimize-git-performance-in-azure-repos

### 要約
Azure Repos の Git リポジトリの健全性を調べ、肥大化や clone／fetch の遅さを改善する新しいガイダンスが公開されました。大きなバイナリの直接コミット、生成テキストの不安定な並び順、不要なブランチを含む clone がパフォーマンスを悪化させる例として示されています。

### 開発者にとって重要なこと
これらの習慣はリポジトリの成長や開発者全員の取得時間に影響します。ブランチを絞った clone などで転送量を減らせる一方、リポジトリの運用ルールや生成物の扱いはチームで揃える必要があります。

### アクションプラン
- Azure Repos の最適化ガイドに沿ってリポジトリの健全性と容量増加要因を調査する。
- 大容量バイナリを Git に直接追加していないか確認し、生成テキストは安定した順序で出力するようにする。
- 全ブランチが不要な作業では `git clone --single-branch` などを検討し、取得時間と転送量を比較する。

### リファレンス
- [New guidance to optimize Git performance in Azure Repos](https://devblogs.microsoft.com/devops/new-guidance-to-optimize-git-performance-in-azure-repos)

## Do AI coding agents struggle with non-REST APIs?

- **Blog:** Blog
- **Author:** Waldek Mastykarz
- **URL:** https://devblogs.microsoft.com/blog/do-ai-coding-agents-struggle-with-non-rest-apis

### 要約
6モデルによる1,356回の実験では、API ドキュメントを参照できる場合、エージェントは REST、POST-only、RPC 形式の API を同程度の成功率・コストで扱えました。一方、ドキュメントなしでは REST は規約からエンドポイントを推測できたものの、RPC 形式ではテストしたモデルがタスクを完了できず、API スタイルよりドキュメントの発見可能性が重要だと報告しています。

### 開発者にとって重要なこと
エージェント利用を理由に既存の非 REST API を REST に書き換える必要はない、という結果です。ただし、ドキュメントが見つからない場合はエージェントが正しい操作を発見できないため、README や OpenAPI 定義から API 仕様へ辿れることが重要です。結果は特定のモック API、モデル、実験条件に基づく点にも留意してください。

### アクションプラン
- API の README や開発者向けドキュメントから OpenAPI 定義や操作リファレンスへのリンクを追加し、エージェントが仕様を取得できるようにする。
- 非 REST API を維持する場合は、ルート URL やエラー応答で利用可能な操作を案内する方法も検討する（記事では今後の検証案として提示）。
- エージェント評価では「仕様を正しく使えるか」と「仕様なしで操作を発見できるか」を分けて測定する。

### リファレンス
- [Do AI coding agents struggle with non-REST APIs?](https://devblogs.microsoft.com/blog/do-ai-coding-agents-struggle-with-non-rest-apis)
