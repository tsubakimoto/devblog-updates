## SharePoint Framework (SPFx) roadmap update – September 2026

- **Blog:** Microsoft365dev
- **Author:** Vesa Juvonen
- **URL:** https://devblogs.microsoft.com/microsoft365dev/sharepoint-framework-spfx-roadmap-update-september-2026

### 要約
Microsoft 365 Copilot 内にチャート、フォーム、KPI、マップなどのインタラクティブな UI を表示できる **Copilot UX components** の一般提供を、SharePoint Framework 1.24 とともに 2026 年 10 月に予定しています。現在は全テナントで利用できるパブリック プレビューで、SPFx の既存のホスティング、React/JavaScript、シングル サインオンを活用して開発できます。

### 開発者にとって重要なこと
既存の SharePoint Web パーツやポータルの業務画面を、エージェント経由で Copilot の会話内に表示する選択肢になります。ユーザーが生成テキストだけでなく決定論的なデータを確認し、承認や送信を行えるため、業務アプリの AI 化と人による確認を同じ体験に組み込めます。

### アクションプラン
- Microsoft365dev の開発チームは、提供予定の SPFx 1.24 と Copilot UX components のサンプルを使い、既存の Web パーツをインライン表示・全画面表示へ移行できるか評価する。
- パブリック プレビューでサンプルをデプロイし、Copilot Workbench、権限、API 呼び出し、ユーザー確認が必要な業務フローを検証する。
- ⚠️ 一般提供時期は 2026 年 10 月予定で、GA のライセンスは未確定のため、導入計画と費用見積もりは続報で更新する。

- **Blog:** Azure Sdk
- **Author:** Kristen Womack
- **URL:** https://devblogs.microsoft.com/azure-sdk/azure-developer-cli-azd-september-2026

### 要約
Azure Developer CLI (`azd`) 1.33.0〜1.34.2 の 9 月リリースでは、依存関係を考慮した拡張機能のアンインストール、拡張機能 API の安定版・プレビュー版契約、`azure.yaml` のインフラストラクチャ／サービス階層、フェーズごとの並列実行数制限が追加されました。Unix ドメイン ソケットや Windows named pipe による外部認証、アーカイブ済みテンプレートへの警告、ACR ビルド診断なども含まれ、セキュリティ改善も実施されています。

### アクションプラン

- 拡張機能の依存関係を `azd extension show` で確認し、不要な拡張機能を `--no-dependencies` などの意図したオプションで整理する。
- ⚠️ セキュリティ改善を含むため、チームで利用する CLI の更新期限を設定する。

## Introducing DxTimingCaptureLibrary

- **Blog:** Directx
- **Author:** Austin Kinross
- **URL:** https://devblogs.microsoft.com/directx/introducing-dxtimingcapturelibrary

### 要約
DirectX の ETW イベントを解釈・相関し、アプリケーションのコールバックへ渡すオープンソース C++ ライブラリ **DxTimingCaptureLibrary** が MIT ライセンスで公開されました。GPU タイミング、リソースの作成・破棄、レジデンシー／ページング、DirectStorage、D3D12 の失敗ログ、VSync、PIX マーカーなどを取得でき、Windows 10 と 11 の全バージョンに対応します。

### 開発者にとって重要なこと
ゲームや DirectX ベースのアプリの開発者は、PIX Timing Captures 由来の処理を自前のゲーム内プロファイラーや Perfetto 出力へ組み込めます。GPU 競合、VRAM の断片化、ページング、パイプライン状態コンパイルなどの実行時情報を、専用ツールだけでなく製品固有の計測フローで分析できます。

### アクションプラン
- DirectX 開発チームは GitHub リポジトリの Quickstart とサンプルを確認し、ETW セッション設定、イベントハンドラー、必要なコールバックを最小構成で試す。
- 既存のプロファイラーに GPU タイミングまたはレジデンシー情報を取り込み、Perfetto や社内のトレース形式へ出力できるか検証する。
- リテール環境で利用する場合は、ETW の権限・オーバーヘッド・収集データの扱いを製品要件に照らして確認する。

### リファレンス
- [Introducing DxTimingCaptureLibrary](https://devblogs.microsoft.com/directx/introducing-dxtimingcapturelibrary)

## Updates to Copilot Code Reviews for Azure Repos

- **Blog:** DevOps
- **Author:** Dan Hellem
- **URL:** https://devblogs.microsoft.com/devops/updates-to-copilot-code-reviews-for-azure-repos

### 要約
パブリック プレビュー中の Azure Repos 向け Copilot Code Review に、レビューの深さとコストを調整する Effort level が追加され、プロジェクトまたはリポジトリ単位で Lite／Balanced の既定値を設定できるようになりました。提案の適用・コミット時に関連コメントをまとめて解決できるようになり、有効化、エージェント プール、カスタム指示、Effort level、ブランチ ポリシーの変更を Azure DevOps 監査ログで追跡できます。

### 開発者にとって重要なこと
Azure Repos を使うチームは、レビューの品質・待ち時間・課金のバランスをリポジトリごとに制御できます。管理者は監査ログによって、どこでレビューが有効化され設定が変更されたかを把握できるため、AI レビューを既存のガバナンスに組み込みやすくなります。

### アクションプラン
- Azure DevOps 管理者はプロジェクト／リポジトリの既定 Effort level を定め、重要度の高いリポジトリだけ高いレビュー深度を選ぶ運用を試す。
- 監査ページで Copilot Code Review の有効化、カスタム指示、エージェント プール、ブランチ ポリシーの変更を確認し、課金と権限の監視に組み込む。
- コメント解決の新しいフローを試し、提案を人が確認してからコミット・解決するレビュー手順をチーム標準に反映する。
- 機能は順次ロールアウト中で、全顧客への提供には 2〜3 週間かかる見込みである点に留意する。

### リファレンス
- [Updates to Copilot Code Reviews for Azure Repos](https://devblogs.microsoft.com/devops/updates-to-copilot-code-reviews-for-azure-repos)

## Windows on AArch64 also provides for hot-patching, but it’s much simpler than on x86

- **Blog:** Oldnewthing
- **Author:** Raymond Chen
- **URL:** https://devblogs.microsoft.com/oldnewthing/20260930-00/?p=112744

### 要約
Windows on AArch64 (arm64) でも関数のホットパッチ用パッチポイントが用意されますが、固定長 4 バイト命令のため x86 より単純です。関数の前に 12 バイトの領域を置き、`adrp`、`add`、`br` の 3 命令で置換先へ分岐するトランポリンを作り、関数先頭は 1 命令の分岐でその領域へ移ります。

### 開発者にとって重要なこと
ARM64 上の Windows バイナリを書き換えるツール、プロファイラー、互換レイヤー、ホットパッチ機構を実装する開発者に、命令境界と ABI の前提を理解する手掛かりを与えます。`xip0` が分岐で破壊可能な scratch レジスターであることや、先頭に pointer authentication 命令が現れる可能性も重要です。

### アクションプラン
- ARM64 の計測・パッチング実装では、命令ポインターが 4 バイト境界にあること、12 バイトのパッチ領域、トランポリンのレジスター破壊規約を確認する。
- 自作のバイナリ書き換え処理は、ARM64 の pointer authentication、命令キャッシュ、スレッド競合を含む実機テストで検証する。
- この記事の説明を一般化せず、対象 Windows ビルドと公式の ABI／命令仕様を併せて参照する。

### リファレンス
- [Windows on AArch64 also provides for hot-patching, but it’s much simpler than on x86](https://devblogs.microsoft.com/oldnewthing/20260930-00/?p=112744)

## Azure Cosmos DB Migration Guide for Elasticsearch Users

- **Blog:** Cosmosdb
- **Author:** Madeline Egan
- **URL:** https://devblogs.microsoft.com/cosmosdb/azure-cosmos-db-migration-guide-for-elasticsearch-users

### 要約
Azure Cosmos DB の組み込みフルテキスト検索、ベクトル検索、ハイブリッド検索を使い、Elasticsearch と運用データベースを一つのマネージドサービスへ統合する移行方針を解説しています。フレーズ検索、BM25 ランキング、ページング、ファセットなどの対応状況を整理する一方、ヒット強調、スコア説明、高度なオートコンプリート、同義語管理などは未対応またはアプリ側実装が必要です。

### 開発者にとって重要なこと
すでに Cosmos DB に運用データがあるチームは、同期用データ経路と検索クラスターを減らせる可能性があります。ただし検索はデータベースのパーティション、インデックス、クエリ形状、RU 消費と一体で設計する必要があり、Elasticsearch と完全な機能互換ではありません。

### アクションプラン
- 検索チームは既存の Elasticsearch クエリを機能表と照合し、未対応機能をアプリ側で補うのか、Elasticsearch を残すのかを決める。
- 代表的なデータ量・検索条件・同時実行数で、Cosmos DB のインデックス、パーティション、RU、レイテンシーを測定する。
- フルテキスト検索とベクトル検索を組み合わせる場合は、RRF、ページング、ランキング品質を実データで評価する。
- 今後の移行シリーズでマッピング移行とクエリ変換が扱われるため、段階的な PoC の入力として利用する。

### リファレンス
- [Azure Cosmos DB Migration Guide for Elasticsearch Users](https://devblogs.microsoft.com/cosmosdb/azure-cosmos-db-migration-guide-for-elasticsearch-users)

## Bring your plugin to Microsoft Copilot with Work IQ Developer Tools

- **Blog:** Microsoft365dev
- **Author:** Seth T. Bacon
- **URL:** https://devblogs.microsoft.com/microsoft365dev/bring-your-plugin-to-microsoft-copilot-with-wiqd

### 要約
Work IQ Developer Tools (WIQD) を使い、既存の Agent Plugins 形式のスキルや MCP サーバーを Microsoft Copilot プラグインへ取り込む方法と、新規プラグインを作成する方法が紹介されました。`wiqd plugin import/create/add/validate/provision/package/share` による開発から検証、Microsoft 365 へのプロビジョニング、組織内共有までの流れを提供します。

### 開発者にとって重要なこと
既存のエージェントや MCP ベースの資産を Microsoft Copilot 向けに再利用し、スキルとコネクターを一つの配布可能なパッケージにできます。ただしプラグインは Copilot の各サーフェスで同じ実行体験になるとは限らず、WIQD の `plugin` コマンド面もパブリック プレビューです。

### アクションプラン
- Copilot／MCP 開発チームは既存プラグインを `wiqd plugin import` で取り込み、スキル、コネクター認証、プライバシー URL、利用規約 URL を確認する。
- 新規プラグインはローカル検証後に `auth login`、`plugin provision`、`plugin package`、`validate --mode deep` の順で検証する。
- 対象となる Copilot サーフェスごとに機能対応、認証、データ権限、ユーザー共有範囲を確認してから `users` または `tenant` スコープで共有する。
- ⚠️ プレビュー API の変更を見込んで、生成されたマニフェストとパッケージをバージョン管理し、公開前に Microsoft 365 と Partner Center の要件を確認する。

### リファレンス
- [Bring your plugin to Microsoft Copilot with Work IQ Developer Tools](https://devblogs.microsoft.com/microsoft365dev/bring-your-plugin-to-microsoft-copilot-with-wiqd)

## Cosmos DB Mirroring in Fabric Now Supports Virtual Network Data Gateways

- **Blog:** Cosmosdb
- **Author:** Jai Maldonado
- **URL:** https://devblogs.microsoft.com/cosmosdb/cosmos-db-mirroring-in-fabric-now-supports-virtual-network-data-gateways

### 要約
Microsoft Fabric の Azure Cosmos DB mirroring が、ユーザーの仮想ネットワーク内にプロビジョニングする Virtual Network Data Gateway に対応しました。これにより、プライベート エンドポイントまたは仮想ネットワークで保護した Cosmos DB の公開ネットワークアクセスを無効にしたまま、OneLake へのレプリケーションを構成できます。

### 開発者にとって重要なこと
ネットワーク分離や規制要件のある企業は、Fabric のサービス タグ IP 範囲を一時的に Cosmos DB のファイアウォールへ追加する運用を避けられます。データ プレーンは専用サブネットとプライベート DNS を通り、制御プレーンは信頼済み Fabric ワークスペースとして認可します。

### アクションプラン
- データ基盤チームは専用の `/27` 以上の委任済みサブネット、プライベート DNS、Microsoft Entra ID への送信経路、OAuth 認証を準備する。
- Microsoft.PowerPlatform リソース プロバイダー、Cosmos DB データプレーン権限、`EnableFabricNetworkAclBypass`、Fabric ワークスペースの信頼設定を順に構成する。
- 現時点ではポータルの新しいミラー作成画面が Virtual network 接続を表示せず、Fabric REST API で作成する必要がある点をチーム手順に明記する。
- ⚠️ 既存のミラーを仮想ネットワーク接続へ付け替えられないため、採用時は新しいミラーの再作成、切り替え、データ整合性を計画する。

### リファレンス
- [Cosmos DB Mirroring in Fabric Now Supports Virtual Network Data Gateways](https://devblogs.microsoft.com/cosmosdb/cosmos-db-mirroring-in-fabric-now-supports-virtual-network-data-gateways)
