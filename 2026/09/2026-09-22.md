## Faster C++ code intelligence for Copilot CLI with Whole Codebase Indexing

- **Blog:** Cppblog
- **Author:** Sinem Akinci
- **URL:** https://devblogs.microsoft.com/cppblog/faster-c-code-intelligence-for-copilot-cli-with-whole-codebase-indexing

### 要約
GitHub Copilot CLI の C++ コードインテリジェンスで、Microsoft C++ Language Server による Whole Codebase Indexing (WCI) が利用可能になりました。`compile_commands.json` を基にシンボルや参照関係を永続的に索引化するため、定義・参照の検索、呼び出し経路の追跡、大規模リポジトリの変更影響分析を繰り返し解析せずに行えます。WCI は既定で有効で、初回は時間とメモリを追加で消費する場合があります。

### 開発者にとって重要なこと
C++ の大規模コードベースや、同じワークスペースで複数のエージェントを動かすチームでは、コード理解とナビゲーションの再解析コストを減らせます。IDE を開かずに Copilot CLI で索引を利用できますが、正確な解析にはビルド構成を反映した `compile_commands.json` が必要です。

### アクションプラン
- C++ プロジェクトに `compile_commands.json` を生成し、Microsoft C++ Language Server と Copilot CLI を設定する。
- 初回索引化の所要時間とメモリ使用量を確認し、`/lsp logs` で進行状況や問題を調査する。
- 大規模リポジトリや並列エージェントのワークフローで、定義・参照検索の速度とリソース使用量を評価する。問題が続く場合は索引の一時無効化を検討する。

### リファレンス
- [Faster C++ code intelligence for Copilot CLI with Whole Codebase Indexing](https://devblogs.microsoft.com/cppblog/faster-c-code-intelligence-for-copilot-cli-with-whole-codebase-indexing)

## Today I will... debug a production crash

- **Blog:** Visual Studio
- **Author:** Aaron Powell
- **URL:** https://devblogs.microsoft.com/visualstudio/today-i-will-debug-a-production-crash

### 要約
本番環境で C# アプリケーションがハングした場合に、スレッドプールの遅延を監視してメモリダンプを取得し、Visual Studio で原因を調べる手順を紹介しています。メモリダンプを「Debug with Mixed」と Parallel Stacks で分析すると、多数のスレッドが同じ箇所でブロックしている状況を特定でき、Copilot にダンプとスレッド状態の分析を支援させることもできます。

### 開発者にとって重要なこと
再現が難しい本番障害でも、実行時のスレッド状態を後から調査する診断手段になります。デスクトップアプリや Web アプリでスレッドプール枯渇・過剰なブロッキングが疑われるチームに関係します。

### アクションプラン
- 本番サービスでスレッドプールの完了遅延を監視し、異常時だけダンプを取得する診断フックを検討する。
- 取得したダンプをアクセス制限された場所で保管し、Visual Studio の「Debug with Mixed」と「Parallel Stacks」で調査する。
- 具体的な再現テストではなく、実際の負荷・スレッド数・ブロッキング箇所をダンプから確認し、必要に応じて Copilot の分析結果を検証する。
- ⚠️ メモリダンプには認証情報やトークンなどの機密データが含まれ得るため、保存期間、権限、取得回数を制限する。

### リファレンス
- [Today I will... debug a production crash](https://devblogs.microsoft.com/visualstudio/today-i-will-debug-a-production-crash)

## Creating a memory dump in C#

- **Blog:** .NET
- **Author:** Aaron Powell
- **URL:** https://devblogs.microsoft.com/dotnet/creating-a-memory-dump-in-csharp

### 要約
C# アプリケーションの応答停止を調査するため、定期的に ThreadPool へタスクを投入し、完了までの時間が閾値を超えたときにプロセスのメモリダンプを作成する実装例を説明しています。Windows の `dbghelp.dll` と Linux の API を使い分ける構成や、フルダンプの作成方法に加え、ダンプの重複生成を抑え、機密情報を含むファイルを安全に扱う注意点も示しています。

### 開発者にとって重要なこと
本番のハングや ThreadPool 飽和を、アプリケーション自身で診断できるようにするための .NET 向け基礎パターンです。Windows と Linux の両方で動くサービスの運用設計や、障害発生後の調査手順に影響します。

### アクションプラン
- アプリケーションの許容遅延に合わせて ThreadPool のプローブ間隔と閾値を設計する。
- Windows/Linux の実行環境ごとにダンプ生成 API と権限を検証し、Visual Studio などの解析環境で開けることを確認する。
- ⚠️ フルダンプは大容量になり得て資格情報・トークン・接続文字列を含むため、制限されたディレクトリ、クールダウン、生成数上限、保持期限を設定する。
- 取得処理が本来の障害を悪化させないよう、ディスク容量・失敗時のログ・監視通知を運用に組み込む。

### リファレンス
- [Creating a memory dump in C#](https://devblogs.microsoft.com/dotnet/creating-a-memory-dump-in-csharp)

## Footprint vs Payload files

- **Blog:** Insidemsix
- **Author:** Howard Kapustein
- **URL:** https://devblogs.microsoft.com/insidemsix/msix-footprint-vs-payload-files

### 要約
MSIX パッケージ内のファイルを、アプリのコード・アセット・データなど配布対象となる「payload files」と、パッケージを記述・検証・補助するメタデータの「footprint files」に分類して説明しています。`AppxManifest.xml`、`AppxBlockMap.xml`、`AppxSignature.p7x` などの footprint ファイルは Packaging API が管理し、payload として追加できない予約名もあります。

### 開発者にとって重要なこと
MSIX のパッケージング、検証、トラブルシューティングで用語を正確に区別でき、API の挙動やパッケージ内容の説明を誤りにくくなります。特に独自のパッケージ生成・検査ツールを保守するチームに有用です。

### アクションプラン
- パッケージ検査ツールやドキュメントで、配布する `.exe`・`.dll`・リソースを payload、予約されたメタデータを footprint として扱う。
- `IAppxPackageWriter::AddPayloadFile()` と `Close()` の責務を確認し、footprint の予約ファイル名を payload として追加しない。
- 曖昧な「content files」という表現は避け、対象が payload か footprint かを明示する。

### リファレンス
- [Footprint vs Payload files](https://devblogs.microsoft.com/insidemsix/msix-footprint-vs-payload-files)

## Using Azure Blob Storage as a durable filesystem for LangChain Deep Agents

- **Blog:** Azure Sdk
- **Author:** Vishnu Charan TJ
- **URL:** https://devblogs.microsoft.com/azure-sdk/using-azure-blob-storage-as-a-durable-filesystem-for-langchain-deep-agents-2

### 要約
LangChain Deep Agents の仮想ファイルシステムを Azure Blob Storage で永続化する `AzureBlobBackend` が紹介されています。エージェントは `ls`、`read_file`、`write_file`、`edit_file` などの使い慣れた操作を行いながら、Blob Storage の耐久性・拡張性・アクセス制御を利用でき、複数エージェントや別プロセスから同じ成果物を共有できます。統合は Public Preview です。

### 開発者にとって重要なこと
長時間・多段階のエージェント処理で、ワーカーローカルのディスクに依存せず、メモリ・スキル・ログ・中間成果物をセッション間で保持できます。企業の文書コーパスや協調エージェントを運用する場合は、Azure RBAC、保持、診断、ライフサイクル管理を既存のストレージ運用に統合できます。

### アクションプラン
- Python 3.11 以降の検証環境で `langchain-azure-storage[deepagents]` を試し、既存の Deep Agents のバックエンドと比較する。
- エージェント用コンテナーを分離し、実行主体に必要最小限の Storage Blob Data Contributor 権限を付与する。Azure ではマネージド ID やワークロード IDを利用する。
- 複数エージェント間の共有ファイル、同時更新、保持期間、復旧、監査ログを検証する。
- ⚠️ Public Preview のため、本番採用前に API の安定性、可用性、データ境界、コストを確認する。

### リファレンス
- [Using Azure Blob Storage as a durable filesystem for LangChain Deep Agents](https://devblogs.microsoft.com/azure-sdk/using-azure-blob-storage-as-a-durable-filesystem-for-langchain-deep-agents-2)

## A brief history of Windows scroll bar shortcuts

- **Blog:** The Old New Thing
- **Author:** Raymond Chen
- **URL:** https://devblogs.microsoft.com/oldnewthing/20260922-00/?p=112719/

### 要約
Windows のスクロールバーにおける操作の歴史を振り返り、右クリックメニューの「Scroll Here」や Shift キーを押しながらのクリックで、クリック位置へ直接移動できるショートカットを説明しています。これらの対応状況はフレームワークごとに異なり、Win32、Chromium、WPF、WinUI、Qt で実装やカスタマイズ性に差があります。

### 開発者にとって重要なこと
スクロールバーを独自 UI で置き換えるアプリでは、ユーザーが期待するキーボード・マウス操作を無意識に失う可能性があります。WinUI など標準コントロールの機能差を把握し、アクセシビリティと操作性を評価する際の参考になります。

### アクションプラン
- 採用中の UI フレームワークで、右クリックメニューと Shift+クリックの挙動を確認する。
- カスタムスクロールバーを実装する場合は、長距離移動、キーボード操作、ポインター操作を一貫して提供する。
- WinUI などで不足する操作が製品に重要なら、代替 UI を設計し、関連するフレームワークの仕様・要望の状況を確認する。

## Foundry hosted agent isolation with Microsoft Agent Framework

- **Blog:** Agent Framework
- **Author:** Roger Barreto
- **URL:** https://devblogs.microsoft.com/agent-framework/foundry-hosted-agent-isolation-with-microsoft-agent-framework

### 要約
Microsoft Foundry のホスト型エージェントで、ユーザー分離とホスト型セッション分離という独立した2つの制御を説明しています。ユーザー分離は誰のデータを扱うか、セッション分離はコードやファイルが継続して存在する VM サンドボックスを表し、直接呼び出し、信頼された中間層、アプリ管理セッション、共有セッションプールに対応できます。

### 開発者にとって重要なこと
会話履歴とサンドボックスの永続状態を別々に設計できるため、マルチユーザーのエージェントでデータ境界と計算資源の共有範囲を明確にできます。ユーザー ID を委任する中間層やセッションプールを構築するアプリケーションでは、ID の安定性、権限、ファイル共有の設計が重要です。AgentServer SDK と .NET/Python の Foundry hosting パッケージはまだ pre-release です。

### アクションプラン
- アプリの認証ユーザーと Foundry の delegated identity の対応を中間層で管理し、各リクエストで安定した値を送る。
- `agent_session_id` をユーザー単位・共有プール単位のどちらで管理するか決め、会話、サンドボックス、永続ファイルの境界をテストする。
- アプリ所有のファイル、データベース行、キャッシュをユーザー ID とセッション ID の組み合わせで分離する。
- ⚠️ SDK とホスティングパッケージが pre-release のため、権限モデル、セッション復元、ファイル共有、API 変更を本番導入前に検証する。

### リファレンス
- [Foundry hosted agent isolation with Microsoft Agent Framework](https://devblogs.microsoft.com/agent-framework/foundry-hosted-agent-isolation-with-microsoft-agent-framework)
