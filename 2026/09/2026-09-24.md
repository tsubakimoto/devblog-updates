## Control where your hosted agent connects with network egress in Foundry Agent Service

- **Blog:** Foundry
- **Author:** Muzz Imam
- **URL:** https://devblogs.microsoft.com/foundry/egress-controls-hosted-agent

### 要約
Microsoft Foundry Agent Service の Hosted Agent に対して、エージェントのコードや個別の HTTP ラッパーとは分離したネットワーク egress ポリシーを設定し、送信先を明示的に許可・拒否する手順が紹介されています。Audit モードで実際の通信を観測した後、Enforced モードで許可された宛先と拒否された宛先をテストする流れです。これは開発・評価向けの Preview であり、GA ではなく、Preview SLA もなく、本番利用を意図していません。

### 開発者にとって重要なこと
外部 API や URL を扱う Hosted Agent では、ツール一覧やアプリケーション側のチェックだけでは実行時の送信先境界を一元的に確認できません。Foundry 側のポリシーをレビュー可能な成果物として管理し、アプリケーションの認証・認可とは別に、監査ログや実通信で境界を検証する設計に関係します。

### アクションプラン
- ⚠️ 本番環境では使用せず、テスト用 Foundry プロジェクトと自分たちが管理する HTTPS エンドポイントで、まず Audit モードの egress ポリシーを評価する。
- 許可する FQDN を最小限の明示的なルールとして定義し、許可された呼び出しと意図的に拒否する呼び出しの両方を Hosted Agent 上でテストする。
- Enforced モードへ移行する場合は、監査用バージョンと分けた新しいポリシー・エージェントバージョンを作成し、通信結果と Application Insights 等の観測結果を確認する。
- 宛先を許可しても API の資格情報や権限は付与されないため、アプリケーション側の認証・認可、リダイレクト制御、秘密情報管理を別途維持する。

## From Chatbots to Automated Agents: Routines in Microsoft Foundry Are Now Generally Available

- **Blog:** Foundry
- **Author:** Linda Li
- **URL:** https://devblogs.microsoft.com/foundry/from-chatbots-to-automated-assistants-routines-in-microsoft-foundry-are-now-generally-available

### 要約
Microsoft Foundry Agent Service の Routines が一般提供になり、エージェントを将来の指定時刻、定期スケジュール、外部イベントに応じて実行できるようになりました。GitHub issue や Microsoft Teams の新しいメッセージへの反応、定期レポートなどを、スケジューラー、キュー、実行履歴、監視を個別に構築せずに Foundry プロジェクトで管理できます。Hosted Agent の reminder tool（Preview）を使えば、長時間処理の完了確認などで同じ会話を後から再開できます。

### 開発者にとって重要なこと
チャット待ちではなく、業務イベントを起点に自律的に動くエージェントを構築するチームが対象です。Routine ごとに作成者の委任 ID とエージェント自身の ID を選択できるため、OAuth などユーザー権限が必要なツールか、マネージド ID やキーで動くツールかに応じた権限設計と監査が必要になります。

### アクションプラン
- GitHub、Teams、定期ジョブ、長時間処理のうち、既存のスケジューラーや webhook 実装を Routines に移行できる対象を洗い出す。
- Routine のトリガー、入力、対象エージェント、実行履歴、失敗時の再実行方針を検証環境で確認する。
- 作成者 ID とエージェント ID のどちらを使うかを、必要な最小権限、OAuth の有無、監査要件に基づいて決める。
- reminder tool を使う場合は Preview であることを踏まえ、同一セッションの継続、重複実行、タイムアウト、通知失敗をテストする。

### リファレンス
- [From Chatbots to Automated Agents: Routines in Microsoft Foundry Are Now Generally Available](https://devblogs.microsoft.com/foundry/from-chatbots-to-automated-assistants-routines-in-microsoft-foundry-are-now-generally-available)

## What’s new in Microsoft Agent Framework: Interactive experiences, memory, and resilient execution

- **Blog:** Agent Framework
- **Author:** Dan Taylor
- **URL:** https://devblogs.microsoft.com/agent-framework/interactive-experiences-memory-and-resilient-execution

### 要約
Microsoft Agent Framework の .NET および Python 向け更新として、AG-UI による対話型 UI、複数チャネルでのエージェントロジック共有、Foundry managed semantic memory、CodeAct による複数ステップ実行、チェックポイントからの再開などが紹介されています。Python では AG-UI 統合が安定版として示され、.NET の AG-UI ホスティング統合は Public Preview です。長時間ワークフローの実行、承認、状態更新、障害からの復旧を組み込みやすくすることが狙いです。

### 開発者にとって重要なこと
単発の質問応答ではなく、ユーザーが進捗やツール実行を確認・承認でき、会話をまたいで記憶し、途中中断から復旧できるエージェントを開発するチームに関係します。AG-UI、Responses、Telegram、A2A、MCP などの接続面を再利用できますが、認証済みユーザーとセッションの対応付け、保存、同時実行制御はアプリケーション側の責務です。

### アクションプラン
- Python または .NET の対象プロジェクトで AG-UI の最小サンプルを動かし、ストリーミング、ツール活動、承認、エラー表示を既存 UI と評価する。
- Foundry Memory や Cosmos DB のメモリ統合を検討する場合は、ユーザー単位の scope を認証済み ID から導出し、保持・削除ポリシーと想起品質を検証する。
- CodeAct や Hyperlight を使う場合は、対応プラットフォーム、実行環境の分離、ツール入力の制限、コスト・遅延を確認する。
- ⚠️ .NET の Preview 機能を本番採用する前に、言語間の機能差と API 変更を確認する。すべてのエンドポイントで認証・認可を実装し、thread ID だけでセッション所有権を判断しない。

### リファレンス
- [What’s new in Microsoft Agent Framework: Interactive experiences, memory, and resilient execution](https://devblogs.microsoft.com/agent-framework/interactive-experiences-memory-and-resilient-execution)

## No, really, you need to pass all unhandled messages to DefWindowProc, part 2

- **Blog:** The Old New Thing
- **Author:** Raymond Chen
- **URL:** https://devblogs.microsoft.com/oldnewthing/20260924-00/?p=112728

### 要約
`RegisterDragDrop` の後に `RevokeDragDrop` を呼んだ Windows アプリケーションでメモリリークに見える現象が発生した事例を、タイムトラベルデバッグで追跡しています。原因は登録解除ではなく、`WM_DESTROY` 後のメッセージをウィンドウプロシージャが状態不足として `0` で返し、`DefWindowProc` に渡していなかったことでした。システムがウィンドウに保持する共有インフラストラクチャのキャッシュは、適切な既定処理を通じて解放されます。

### 開発者にとって重要なこと
Win32 のウィンドウプロシージャを自前実装するアプリケーションでは、未処理メッセージを黙って無視すると、後続のクリーンアップ処理や OS の既定動作を妨げる可能性があります。登録と解除の直後にすべてのメモリが解放されないことは、直ちにリークを意味するわけではありません。

### アクションプラン
- ウィンドウプロシージャで処理しないメッセージを、状態が見つからない場合も含めて `DefWindowProc` に渡しているか確認する。
- `WM_DESTROY` 前後、ドラッグ＆ドロップ登録・解除、遅れて到着するメッセージを含む再現テストを追加する。
- メモリ調査では、登録解除直後の一時的なキャッシュと、ウィンドウ破棄後にも残り続ける実リークを区別する。

## Documentation Is the New Source Code

- **Blog:** ISE
- **Author:** Liza Shakury
- **URL:** https://devblogs.microsoft.com/ise/documentation-is-the-new-source-code

### 要約
AI コーディングアシスタント、エージェント型 CLI、MCP サーバーなどがリポジトリの文書をコンテキストとして読み込む現在、ドキュメントは将来の変更に対するシステムプロンプトの役割を持つという考え方を示しています。リポジトリ全体の指示、スコープ付き指示、Skills、ADR、`docs/`、コード隣接ドキュメントを層として整備し、暗黙の規約を AI に推測させない実践例を説明しています。

### 開発者にとって重要なこと
AI を使った変更の品質はモデルだけでなく、アーキテクチャ、環境変数、開発・CI 手順、エラー処理、ログ、命名、Git 運用などがどれだけ明文化されているかに左右されます。短命なブランチやエージェント作成 PR を運用するチームほど、暗黙知の再現を防ぐリポジトリ内ドキュメントがレビューと CI の手戻りを減らします。

### アクションプラン
- リポジトリ全体で常に必要な規約を `copilot-instructions.md` 等に整理し、アーキテクチャ、必須環境変数、開発・テスト・CI コマンド、横断的な品質ルールを簡潔に記載する。
- バックエンドやフロントエンドなど領域固有の規約は、適用対象を限定した instruction ファイルに分け、Skills には繰り返し実行するワークフローを記録する。
- 重要な設計理由は ADR に残し、機能・運用手順は `docs/` に配置して、AI と人間が検索できるリンクと更新責任者を用意する。
- エージェントに同じ変更を試行させ、規約を追加する前後でレビュー指摘、CI 失敗、修正回数を測定し、文書を継続的に改善する。

### リファレンス
- [Documentation Is the New Source Code](https://devblogs.microsoft.com/ise/documentation-is-the-new-source-code)
