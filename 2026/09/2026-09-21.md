## PostgreSQL to SQL Field Notes: Date & Time

- **Blog:** Azure SQL
- **Author:** Jerry Nixon
- **URL:** https://devblogs.microsoft.com/azure-sql/pg-to-sql-date-time

### 要約
PostgreSQL から SQL Server へ移行する際の日時型の違いを整理した記事です。`timestamp`、`timestamptz`、`datetime2`、`datetimeoffset` の違いを、精度・タイムゾーン・オフセット・保存形式の観点から比較しています。

### 開発者にとって重要なこと
PostgreSQL 由来のアプリやデータ移行では、日時型の選択を誤ると、時刻のずれ、検索条件の不一致、保存精度の劣化につながります。Azure SQL / SQL Server を使うチームは、スキーマ移行時にこの差分を必ず確認する必要があります。

### アクションプラン
- PostgreSQL 側の日時カラムを洗い出し、SQL Server 側の対応型を再確認する
- タイムゾーンを保持すべきデータと、ローカル時刻として扱うデータを分けて設計する
- 移行後のクエリ、並び順、フィルタ条件が期待どおりか検証する
- 詳細なマッピング判断は本文を参照する

### リファレンス
- [PostgreSQL to SQL Field Notes: Date & Time](https://devblogs.microsoft.com/azure-sql/pg-to-sql-date-time)

## What's the highest legal FILETIME ? Is it safe to use?

- **Blog:** Oldnewthing
- **Author:** Raymond Chen
- **URL:** https://devblogs.microsoft.com/oldnewthing/20260921-00/?p=112711

### 要約
`FILETIME` を比較用の番兵値として使いたい場合、どこまでの値が安全かを考える記事です。`CompareFileTime` で常に「後ろ」と扱わせる値をどう選ぶべきか、定義上の制約を踏まえて説明しています。

### 開発者にとって重要なこと
Windows API で `FILETIME` を扱うコード、特にソート・比較・期限判定・番兵値設計をしている実装に関係します。境界値の選び方を誤ると、比較結果や永続化データの解釈が壊れる可能性があります。

### アクションプラン
- `FILETIME` を番兵値として使っているコードがあれば、選定値が定義上安全か見直す
- 比較ロジック、シリアライズ、境界条件テストを追加する
- 必要なら本文の定義説明を確認して、独自の仮定を置かない

### リファレンス
- [What's the highest legal FILETIME ? Is it safe to use?](https://devblogs.microsoft.com/oldnewthing/20260921-00/?p=112711)

## Knowledge cutoff is a poor proxy for model capability

- **Blog:** Blog
- **Author:** Waldek Mastykarz
- **URL:** https://devblogs.microsoft.com/blog/knowledge-cutoff-is-a-poor-proxy-for-model-capability

### 要約
モデルの knowledge cutoff は、学習データの最終時点を示すにすぎず、実際の製品知識や実務能力を正確には表さない、という論点の記事です。製品に関する質問であっても、知識の有無はモデルごとに大きく異なりうることを示しています。

### 開発者にとって重要なこと
LLM の選定や評価を、単純な knowledge cutoff の新しさだけで判断すると、実際の品質を見誤ります。AI 機能を組み込むチームは、対象タスクに対する実測評価を優先する必要があります。

### アクションプラン
- モデル選定を knowledge cutoff だけで決めず、実タスクでベンチマークする
- 自社製品や業務ドメインに関する質問での応答品質を確認する
- 運用で使うモデルは、更新日よりも性能・再現性・ガードレールを基準に評価する

### リファレンス
- [Knowledge cutoff is a poor proxy for model capability](https://devblogs.microsoft.com/blog/knowledge-cutoff-is-a-poor-proxy-for-model-capability)

## Spec-Driven Development comes to Azure Cosmos DB: The First Database Extension for GitHub Spec Kit

- **Blog:** Cosmosdb
- **Author:** Theo van Kraay
- **URL:** https://devblogs.microsoft.com/cosmosdb/spec-driven-development-comes-to-azure-cosmos-db-the-first-database-extension-for-github-spec-kit

### 要約
Azure Cosmos DB に、GitHub Spec Kit 向けの最初のデータベース拡張として spec-driven development を導入する内容です。AI コーディングエージェントがコードを書けても、パーティションキー、アクセスパターン、クライアント設定などの設計判断は開発者がレビューすべきだと述べています。

### 開発者にとって重要なこと
Cosmos DB アプリを AI 支援で作るチームでは、コード生成だけでなく設計レビューがコスト・性能・信頼性に直結します。Spec Kit ベースのワークフローを使う場合も、データモデルと運用前提の確認が欠かせません。

### アクションプラン
- Cosmos DB の設計レビューで、パーティションキーとアクセスパターンを先に確認する
- AI 生成コードを受け入れる前に、クライアント設定とスケーリング前提を検証する
- Spec Kit ワークフローが既存の開発プロセスに合うか、チームで試す
- 詳細な導入手順は本文を参照する

### リファレンス
- [Spec-Driven Development comes to Azure Cosmos DB: The First Database Extension for GitHub Spec Kit](https://devblogs.microsoft.com/cosmosdb/spec-driven-development-comes-to-azure-cosmos-db-the-first-database-extension-for-github-spec-kit)
