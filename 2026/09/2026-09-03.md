## SQL Decomposition in a Nutshell

- **Blog:** Azure SQL
- **Author:** Jerry Nixon
- **URL:** https://devblogs.microsoft.com/azure-sql/sql-decomposition

### 要約
SQL の分解、カプセル化、明示的な依存関係という考え方を、T-SQL の文脈で説明する記事です。アプリ開発で「1つの関数にやらせすぎる」と保守しづらくなるのと同じように、SQL でも責務を分けることの価値を取り上げています。

### 開発者にとって重要なこと
Azure SQL や T-SQL を使うチームにとって、クエリやストアドプロシージャの保守性・テスト容易性・変更安全性に直結する話題です。複雑な SQL ロジックを抱えるアプリでは、レビューや障害対応の負担を減らす観点で特に重要です。

### アクションプラン
- Azure SQL / T-SQL の大きな処理を、責務ごとに分割できるか見直す
- テストしにくい SQL がある場合は、依存関係を明示できる構造に置き換える
- 既存のクエリやプロシージャで、読みやすさと変更しやすさを優先して整理する

### リファレンス
- [SQL Decomposition in a Nutshell](https://devblogs.microsoft.com/azure-sql/sql-decomposition)

## Advocating for Uptime: The 6 Phases of Change

- **Blog:** Azure SQL
- **Author:** Jerry Nixon
- **URL:** https://devblogs.microsoft.com/azure-sql/schema-change

### 要約
スキーマ変更は避けられず、運用中のデータベースでは段階的に進める必要があるという内容です。タイトルの通り、停止時間を抑えながら変更を進めるための「変化の 6 段階」を扱う記事です。

### 開発者にとって重要なこと
Azure SQL を本番で運用するチーム、特に頻繁にスキーマ変更を行うサービスに関係します。マイグレーション設計、互換性維持、デプロイ手順の見直しに直接つながります。

### アクションプラン
- ⚠️ 本番 DB の変更手順が段階的更新になっているか確認する
- 破壊的なスキーマ変更がある場合は、先に互換性確保と移行計画を作る
- 変更時の可用性要件を整理し、停止時間を前提にしない運用へ寄せる

### リファレンス
- [Advocating for Uptime: The 6 Phases of Change](https://devblogs.microsoft.com/azure-sql/schema-change)

## Test what you ship: MSTest and Native AOT

- **Blog:** .NET
- **Author:** Amaury Levé
- **URL:** https://devblogs.microsoft.com/dotnet/mstest-source-generation

### 要約
MSTest のソース生成により、テストプロジェクトでも Native AOT と trimming のデプロイモデルに合わせやすくなることを紹介しています。テスト実行経路からリフレクションを減らせる点がポイントです。

### 開発者にとって重要なこと
.NET で Native AOT や trimming を使うアプリを開発しているチーム、またはそのテスト基盤を持つチームに関係します。実際の配布モデルに近い形でテストできるため、実行時差異の発見や互換性確認に役立ちます。

### アクションプラン
- .NET テストが Native AOT / trimming 対応を前提にしているか確認する
- MSTest を使っているなら、ソース生成の導入可否を評価する
- 本番の配布モデルに近い設定でテストが動くか、CI で検証する

### リファレンス
- [Test what you ship: MSTest and Native AOT](https://devblogs.microsoft.com/dotnet/mstest-source-generation)

## The case of the progress callback that never got called when progress happened

- **Blog:** Oldnewthing
- **Author:** Raymond Chen
- **URL:** https://devblogs.microsoft.com/oldnewthing/20260903-00/?p=112672

### 要約
進捗ハンドラーを登録したのに、進捗が発生したタイミングで呼ばれなかった理由を扱う技術記事です。非同期処理とイベント登録のタイミングに関する落とし穴を、具体例ベースで解説しています。

### 開発者にとって重要なこと
C# の async/await や進捗通知を扱うアプリ、UI、SDK 開発に関係します。コールバック登録の順序や、非同期オブジェクトのライフサイクルに起因する不具合を避けるヒントになります。

### アクションプラン
- 非同期 API のコールバック登録順序を見直し、取りこぼしがないか確認する
- progress/event 系の処理を、再現テスト付きで点検する
- 進捗通知に依存する UI やジョブ管理コードで、待ち合わせ条件を明確にする

### リファレンス
- [The case of the progress callback that never got called when progress happened](https://devblogs.microsoft.com/oldnewthing/20260903-00/?p=112672)
