## Connect Azure Functions to more services with managed connectors

- **Blog:** Azure SDK Blog
- **Author:** Lily Ma
- **URL:** https://devblogs.microsoft.com/azure-sdk/connect-azure-functions-to-more-services-with-managed-connectors/

### 要約
Azure Functions の managed connectors により、Microsoft 365、Teams、SharePoint、Dataverse など約 1,700 のサービスをトリガーや型付きクライアントから利用できます。Webhook 登録や OAuth トークン管理を Azure Connector Namespace に任せ、関数側では業務ロジックを実装できます。記事では SharePoint の RFP 文書を処理し、Azure Content Understanding で解析して Teams に通知する .NET のサンプルを紹介しています。

### 開発者にとって重要なこと
外部サービス連携を含むイベント駆動アプリを Azure Functions で構築するとき、個別の接続処理を実装せずに連携先を広げられます。現時点では **パブリックプレビュー** で、.NET isolated、Python、Node.js が対象です。利用できる言語、ホスティングプラン、リージョンを事前に確認してください。

### アクションプラン
- Azure Functions から外部サービスへのイベント連携が必要な場合、managed connectors の対象サービスと現在のプレビュー制約を確認する。
- 公開されている RFP intake サンプルを使い、接続設定、イベント処理、エラー処理を含む実装方法を評価する。
- カスタムコードが少なく、コネクタ処理のオーケストレーションが中心なら、Azure Logic Apps も比較する。

### リファレンス
- [Connect Azure Functions to more services with managed connectors](https://devblogs.microsoft.com/azure-sdk/connect-azure-functions-to-more-services-with-managed-connectors/)

## UWP and WinUI 3 apps: UI testing with MSTest

- **Blog:** .NET Blog
- **Author:** Amaury Levé
- **URL:** https://devblogs.microsoft.com/dotnet/testing-uwp-and-winui-3-apps-with-mstest/

### 要約
MSTest 4.5 と Microsoft.Testing.Platform 2.5 を使い、UWP および WinUI 3 アプリで UI ディスパッチャー上のテストを実行する方法を解説しています。パッケージの有無や AppContainer の利用に応じた起動方式が示され、`[UITestMethod]` では初期化、非同期テスト本体、後処理を UI スレッド上で実行できます。パッケージ化・サンドボックス化されたテストでは sidecar controller が起動や結果報告を担い、従来の VSTest 配置ランタイムには依存しません。

### 開発者にとって重要なこと
UWP／WinUI 3 の UI テストで必要な実際の UI dispatcher を使ったテスト構成が明確になり、アプリのパッケージ形態に応じて MTP の起動経路を選べます。パッケージ化アプリの起動には Developer Mode などのポリシーが必要な場合があり、ローカルで成功しても CI エージェントで動くとは限りません。

### アクションプラン
- UWP／WinUI 3 のテストプロジェクトでは、MSTest.Sdk 4.5 と Microsoft.Testing.Platform を選択し、アプリモデルに合ったプロジェクト設定と起動方法を確認する。
- UI 操作を行うテストには `[UITestMethod]` を用い、初期化・テスト・後処理が UI dispatcher にアクセスできることを検証する。
- パッケージ化または AppContainer のテストは、Developer Mode／サイドローディング設定、実行ユーザー、必要なフレームワークを CI エージェント上で検証する。AppContainer テストは非昇格で実行する。

### リファレンス
- [UWP and WinUI 3 apps: UI testing with MSTest](https://devblogs.microsoft.com/dotnet/testing-uwp-and-winui-3-apps-with-mstest/)

## From an Empty Folder to an AI Agent: Meet create-cosmos-agent

- **Blog:** Azure Cosmos DB Blog
- **Author:** Sajeetharan Sinnathurai
- **URL:** https://devblogs.microsoft.com/cosmosdb/from-an-empty-folder-to-an-ai-agent-meet-create-cosmos-agent/

### 要約
`create-cosmos-agent` は、TypeScript API と React UI を備えた AI エージェントアプリを生成するオープンソース CLI です。初期状態では決定論的なモック AI、ローカル ID、インメモリストレージを使うため、Azure サブスクリプションやモデルキーなしで試せます。テナント／ユーザー分離、メモリ検索と引用、承認付きアクション、診断・テスト、Cosmos DB や Azure への移行用構成も含まれます。

### 開発者にとって重要なこと
チャットのデモだけでなく、メモリ、テナント境界、認証、テスト、デプロイまで含むエージェント開発の土台をローカルから評価できます。生成された構成がそのまま本番要件を満たすとは限らず、ID、モデル、リージョン容量、権限、コストなどは個別に判断する必要があります。

### アクションプラン
- TypeScript でエージェントアプリを検討中なら、`npx create-cosmos-agent@latest bootstrap my-agent --yes` で生成し、まずローカルの構成と実行体験を評価する。
- 本番利用を検討する場合、テナント分離、メモリ検索、承認境界を確認し、`doctor` と `validate` を実行して構成・セキュリティ・型チェック・テストを検証する。
- Azure へ移行する前に、Microsoft Entra ID／Managed Identity、Cosmos DB の容量とロール、モデルの利用可否・リージョンクォータ、デプロイ費用を確認する。

### リファレンス
- [From an Empty Folder to an AI Agent: Meet create-cosmos-agent](https://devblogs.microsoft.com/cosmosdb/from-an-empty-folder-to-an-ai-agent-meet-create-cosmos-agent/)

## If somebody tries to hot-patch an already-hot-patched function, how do they avoid conflicts?

- **Blog:** The Old New Thing
- **Author:** Raymond Chen
- **URL:** https://devblogs.microsoft.com/oldnewthing/20261005-00/?p=112755/

### 要約
Windows の hot-patching は、対応システムで Windows Update が予約領域を使って安全と判定された関数を置き換えるための仕組みであり、複数の独立した hot-patcher による重ねがけを想定していません。許可されていないコードによるパッチを検出すると、対象ファイルを hot-patch 不可として再起動が必要になる可能性があります。事前検査後に別のパッチが入り、処理が途中で失敗すると、メモリ上のバイナリが部分的にパッチされた状態になるリスクも説明しています。

### 開発者にとって重要なこと
hot-patch 用の領域は Windows Update の管理下にあるもので、アプリや別のパッチャーが利用すると更新処理と競合し、復旧や再起動が必要になり得ます。データ構造のレイアウトや不変条件を変える更新など、すべての変更が hot-patch 可能なわけではありません。

### アクションプラン
- ⚠️ アプリケーションや独自の更新機構で hot-patch 用領域を変更・利用しない。更新は OS が想定する Windows Update の経路に委ねる。
- Windows Server または Windows 11 Enterprise の hotpatch 運用では、対象更新が hot-patch 対応であることと、更新後に再起動が必要となる条件を確認する。

## I’m the Only Developer on This Project. Do I Really Need RBAC?

- **Blog:** Azure Cosmos DB Blog
- **Author:** Sudhanshu Khera
- **URL:** https://devblogs.microsoft.com/cosmosdb/im-the-only-developer-on-this-project-do-i-really-need-rbac/

### 要約
開発者が一人でも、継続して使う Azure Cosmos DB のライブプロジェクトでは、アカウントキーより Microsoft Entra ID とデータプレーン RBAC を使うことが推奨されています。アプリの ID に必要なデータロールだけをデータベースやコンテナー単位で割り当てることで、キーの保管・ローテーションの負担を減らし、アプリのアクセス範囲を限定できます。既存のキー認証を移行するときは、依存する経路を一つずつ切り替えて動作を確認してから、アカウント全体のキー認証を無効化する手順を紹介しています。

### 開発者にとって重要なこと
RBAC の価値はチームの人数ではなく、アプリが開発者本人の広い権限やアカウントキーを引き継がないようにすることです。RBAC も誤操作を防ぐものではなく、Data Contributor は対象範囲内の削除も可能なため、最小スコープの割り当てやバックアップなどは引き続き必要です。

### アクションプラン
- 新規のライブ環境では、ローカル実行に開発者 ID、対応する Azure ホスト上のアプリに Managed Identity を使い、それぞれに必要最小限の Cosmos DB データロールを割り当てる。
- 既存環境はアプリ、ノートブック、定期ジョブ、保守スクリプトなどの依存先を洗い出し、一つの経路ずつ ID 認証に切り替えて必要な読み書きを検証する。
- ⚠️ 全経路の切り替えと検証が完了するまではキー認証を無効化しない。無効化はアカウント全体に影響するため、旧キーの削除も検証後に行う。

### リファレンス
- [I’m the Only Developer on This Project. Do I Really Need RBAC?](https://devblogs.microsoft.com/cosmosdb/im-the-only-developer-on-this-project-do-i-really-need-rbac/)
