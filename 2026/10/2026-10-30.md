## Everything released in October 2026 for Azure Developer CLI

- **Blog:** Azure SDK
- **Author:** Kristen Womack
- **URL:** https://devblogs.microsoft.com/azure-sdk/azure-developer-cli-azd-october-2026

### 要約
Azure Developer CLI (`azd`) の 10 月リリース 1.35.0〜1.37.2 では、デプロイ前のプレビュー、Container Apps express へのイメージデプロイ、環境変数の保存値を削除する beta コマンドなどが追加されました。拡張機能向け API の安定化や拡張機能のインストール・キャンセル処理の改善に加え、環境・状態関連の Go API に破壊的変更があり、セキュリティ改善も含まれています。

### 開発者にとって重要なこと
`azd deploy --preview` で複数の Azure サービスへのデプロイ対象を事前に確認でき、Container Apps express にも対応します。一方、独自の `azd` 拡張機能や環境・状態 API を利用する Go コードは移行が必要です。`azd env unset` は beta 機能で、非対話実行には `--force` が必要です。

### アクションプラン
- Azure Developer CLI を利用するチームは、1.35.0〜1.37.2 のリリースノートを確認して `azd` の更新を計画し、セキュリティ改善を含むためアップグレードを検討する。
- デプロイ前確認が必要な環境では `azd deploy --preview` を試し、Container Apps express を使う場合は複数リビジョンやトラフィック分割がサポートされない点を確認する。
- 独自の Go 実装で環境・状態 API を使っている場合は、戻り値のエラー処理と `state.NewStateCacheManager` の引数変更を移行ガイドで確認する。拡張機能のパイプライン利用者は必要な拡張機能が生成された定義でインストールされるか確認する。

### リファレンス
- [Everything released in October 2026 for Azure Developer CLI](https://devblogs.microsoft.com/azure-sdk/azure-developer-cli-azd-october-2026)

## Is Azure SQL Database Hyperscale “distributed SQL”?

- **Blog:** Azure SQL
- **Author:** Anna Hoffman
- **URL:** https://devblogs.microsoft.com/azure-sql/is-azure-sql-database-hyperscale-distributed-sql

### 要約
Azure SQL Database Hyperscale は、クエリ処理、ログ、ページサーバー、長期ストレージを分担する分散アーキテクチャですが、書き込みを受け付けるプライマリは 1 つです。記事はこの構成が SQL Server のトランザクションや T-SQL 互換性を保ちつつ、ストレージと読み取りのスケールを提供すると説明し、Aurora PostgreSQL とのベンチマーク結果も紹介しています（比較試験は Microsoft 委託と明記されています）。

### 開発者にとって重要なこと
「分散 SQL」という名称だけで複数ノード書き込みを期待せず、必要な一貫性、SQL 互換性、読み取り・書き込み性能を分けて評価することが重要です。Hyperscale は最大 128 TB のストレージや名前付きレプリカによる読み取り用途の分離を提供しますが、複数ライターが必須のワークロードとは設計上のトレードオフが異なります。

### アクションプラン
- データベース選定時は「分散 SQL」に求める要件を、複数ライターの必要性、トランザクション、一貫性、SQL 互換性、運用要件に分けて整理する。
- Hyperscale を検討するチームは、書き込み容量と読み取りスケールを個別に見積もり、記事で紹介されたベンチマークだけで判断せず、公開されている方法論を確認したうえで自分たちのワークロードを測定する。

### リファレンス
- [Is Azure SQL Database Hyperscale “distributed SQL”?](https://devblogs.microsoft.com/azure-sql/is-azure-sql-database-hyperscale-distributed-sql)

## Does ‘eval’ in the workspace path change what your agent does?

- **Blog:** Blog
- **Author:** Waldek Mastykarz
- **URL:** https://devblogs.microsoft.com/blog/does-eval-in-the-workspace-path-change-what-your-agent-does

### 要約
GitHub Copilot CLI を使った約 900 回の実験では、作業ディレクトリ名に `eval` を含めるとエージェントは評価中だと強く意識するものの、実際の行動や作業量に測定可能な差は確認されませんでした。記事は、フォルダー名だけで評価ハーネスを作り直す必要はない一方、評価への意識そのものを測る場合は中立的で現実的な名前を使うよう勧めています。

### 開発者にとって重要なこと
エージェント評価では、モデルの自己申告ではなく、変更差分、テスト結果、ログ、実行コマンドなどの証拠で振る舞いを測る必要があります。パス名が評価への疑念を変えることと、タスク実行を変えることは同じではありません。

### アクションプラン
- エージェント評価環境の担当者は、特別な評価意識を測る目的がなければ `billing-api` のような中立的で現実的な作業ディレクトリ名を使い、`eval` という名前だけを理由にハーネスを変更しない。
- 評価条件を変更するときは一度に一要素だけを変え、事前に差の判定基準を定めたうえで十分な反復を行い、応答内容だけでなく差分やテストなどの実測結果を比較する。

### リファレンス
- [Does ‘eval’ in the workspace path change what your agent does?](https://devblogs.microsoft.com/blog/does-eval-in-the-workspace-path-change-what-your-agent-does)
