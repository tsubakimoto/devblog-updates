## Try SqlClient’s new connection pool for faster parallel connections

- **Blog:** Azure SQL
- **Author:** Malcolm Daigle
- **URL:** https://devblogs.microsoft.com/azure-sql/try-sqlclients-new-connection-pool-for-faster-parallel-connections

### 要約
Microsoft.Data.SqlClient の新しい接続プール Pool V2 は、同じプールに対する複数の新規接続を並行して確立し、コールドスタートやアクセス急増時の接続待ちを減らすことを目指しています。記事のベンチマークでは、同時接続数 100 の条件で従来方式より速い結果が示されていますが、実際の効果はワークロードやネットワーク遅延によって異なります。非同期 API でも一部のネットワーク処理は同期実行されるため、遅延の大きい接続先ではスレッドプールへの影響に注意が必要です。

### 開発者にとって重要なこと
起動時に複数の DB 接続を開くアプリや、トラフィック急増後に接続プールを拡張するサービスで、待ち時間やスレッド使用量を改善できる可能性があります。記事のベンチマークは接続確立を対象とし、クエリ性能やウォームプールの再利用性能を測ったものではありません。

### アクションプラン
- Microsoft.Data.SqlClient を使うアプリでは、Pool V2 の利用条件と有効化方法を本文で確認し、まず負荷試験環境で評価する。
- 起動時や同時接続時の接続確立時間を計測し、従来の `Min Pool Size` 調整やプーリング無効化などの回避策が不要になるか比較する。
- 非同期接続で SQL Server までのネットワーク遅延が大きい場合、マネージドスレッドプールの圧力と DB 操作の同時実行数を監視する。

### リファレンス
- [Try SqlClient’s new connection pool for faster parallel connections](https://devblogs.microsoft.com/azure-sql/try-sqlclients-new-connection-pool-for-faster-parallel-connections)

## PostgreSQL to SQL Field Notes: Connections

- **Blog:** Azure SQL
- **Author:** Jerry Nixon
- **URL:** https://devblogs.microsoft.com/azure-sql/pg-to-sql-connections

### 要約
PostgreSQL から Microsoft SQL（T-SQL）へ移行する開発者向けシリーズの初回として、接続モデルの違いを説明しています。PostgreSQL は接続ごとに OS プロセスを使い、接続数や長時間トランザクションの管理が重要ですが、Microsoft SQL は worker を必要に応じて割り当て、ADO.NET の接続プールも一般に自動管理されます。そのため PostgreSQL で必要だった接続数抑制やプーラーの運用が、移行後も同じ形で必要とは限りません。

### 開発者にとって重要なこと
PostgreSQL での接続制限・アイドル接続・トランザクション管理を前提にした設計が、SQL Server への移行後に適切か再評価できます。ただし接続モデル以外にも DB エンジン間の差異があるため、この記事だけで移行作業全体を判断することはできません。

### アクションプラン
- PostgreSQL から SQL Server への移行を検討する場合、アプリの接続上限、プーリング、PgBouncer の利用、アイドル／長時間トランザクション監視を棚卸しする。
- `Npgsql` と `Microsoft.Data.SqlClient` の接続処理を比較し、接続プール設定とアプリ側の並行処理上限を移行先で再設計する。
- 移行前後で接続数、リソース使用量、トランザクション時間、障害時の挙動を負荷試験し、他の T-SQL／機能差も個別に確認する。

### リファレンス

## Why does the compiler sometimes use ud2 and sometimes int 3 for code that shouldn’t execute?

- **Blog:** The Old New Thing
- **Author:** Raymond Chen
- **URL:** https://devblogs.microsoft.com/oldnewthing/20261006-00/?p=112757/

### 要約
x86 コンパイラーが到達すべきでないコードに `int 3` と `ud2` のどちらを使うか、その目的の違いを解説しています。`int 3` は通常のコードが存在しない領域を示す 1 バイトのブレークポイント命令で、無効な関数ポインターなどによる実行を検知する用途です。一方 `ud2` は未定義動作など、本来到達しないはずの実行経路に到達したことを示します。

### 開発者にとって重要なこと
クラッシュダンプやデバッガでこれらの命令を見たとき、原因調査の方向を絞る手掛かりになります。`ud2` なら到達不能と想定したロジックや未定義動作、`int 3` なら無効な関数ポインターや明示的な／デバッガ挿入ブレークポイントなどを調べます。

### アクションプラン
- `ud2` で停止した場合、該当経路に至る条件や戻り値処理を調べ、未定義動作や到達不能前提が破られていないか確認する。
- `int 3` で停止した場合、関数ポインターの初期化・呼び出し先、ハードコードされたブレークポイント、デバッガのブレークポイントを確認する。
- 命令だけで原因を断定せず、呼び出し履歴とレジスター、シンボルを含むデバッグ情報を合わせて判断する。

- [Why does the compiler sometimes use ud2 and sometimes int 3 for code that shouldn’t execute?](https://devblogs.microsoft.com/oldnewthing/20261006-00/?p=112757/)

## What is Agent Experience (AX)?

- **Blog:** Blog
- **Author:** 記載なし
- **URL:** https://devblogs.microsoft.com/blog/what-is-agent-experience-ax/

### 要約
Agent Experience（AX）は、AI エージェントが技術や製品を発見・選択し、正しく利用できるかという体験です。記事では、製品名を指定しないタスクで選ばれるかを測る「propensity」と、製品を指定したタスクで現行 API などを正しく使えるかを測る「efficacy」を分け、結果の品質と実行コストも評価する考え方を紹介しています。ドキュメント、エージェント拡張、API／SDK／CLI などは、開発者が改善できる要素です。

### 開発者にとって重要なこと
人間向けのドキュメントが整っていても、エージェントが古い API を選ぶ、製品を発見できない、ビルド失敗を成功と扱うといった問題は起こり得ます。ベストプラクティスをそのまま適用するだけでなく、実際のタスク評価で成功率・品質・コストの変化を測る必要があります。

### アクションプラン
- SDK、API、CLI を提供するチームは、製品名を指定しない評価タスクと製品を指定するタスクを作り、選択率と正しい利用率を別々に測定する。
- エージェントが参照するドキュメント、リリースノート、エラーメッセージ、スキャフォルダーを点検し、古い API や成功と誤認される出力がないか確認する。
- 改善案を導入する前後でタスクの品質と実行コストを比較し、エージェント拡張の追加が本当に必要か評価する。
