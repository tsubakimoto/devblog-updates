## Azure DevOps Server RC (26H2) Is Now Available

- **Blog:** DevOps
- **Author:** Gloridel Morales
- **URL:** https://devblogs.microsoft.com/devops/azure-devops-server-rc-26h2-is-now-available

### 要約
Azure DevOps Server 26H2 のリリース候補版（RC）が公開され、Azure DevOps Services で先行提供されていた機能に加え、セキュリティと品質の改善が含まれます。Azure Boards の UI 更新、PR のターゲットブランチ選択、パイプライン実行のデバッグ改善、新しい Test Run Hub が主な変更です。TFS 2015 以降から RC への直接アップグレードが可能で、RC から正式リリース（RTW）への直接アップグレードもサポートされます。

### 開発者にとって重要なこと
オンプレミスで Azure DevOps Server を運用するチームは、ホスト版で利用可能になった機能を自社環境で試せます。RC は本番導入前の検証機会として使えます。また、TFS 2017 の延長サポートは 2027 年 1 月 12 日に終了するため、該当環境の移行計画にも関係します。

### アクションプラン
- テスト用デプロイで RC を評価し、Boards、PR、パイプライン、テスト管理の各ワークフローを確認する。
- 現行バージョンからのアップグレード経路と、RTW への移行手順をリリースノートで確認する。
- TFS 2017 を利用している場合は、サポート終了前の Azure DevOps Server へのアップグレード計画を立てる。本番環境への適用は RC の検証後に判断する。

## External Location

- **Blog:** Insidemsix
- **Author:** Howard Kapustein
- **URL:** https://devblogs.microsoft.com/insidemsix/msix-external-location

### 要約
MSIX の External Location は、MSIX のパッケージ ID などを既存のインストーラー製品に追加しながら、実行ファイルなどのペイロードは別の場所に置く仕組みです。マニフェストに `<uap10:AllowExternalContent>true</uap10:AllowExternalContent>` を設定し、インストール時に `-ExternalLocation` でパスを指定します。MSIX は外部ペイロードの場所を認識しますが、その作成・保護・修復・削除は管理しません。

### 開発者にとって重要なこと
既存インストーラーを全面的に MSIX へ置き換えず、パッケージ ID が必要な Windows 機能などを利用できる可能性があります。一方で、外部ファイルのライフサイクルやセキュリティは既存のインストーラー側の責任として残るため、MSIX が管理するファイルとの境界を明確にする必要があります。

### アクションプラン
- 既存インストーラーに MSIX の機能を組み合わせる必要がある場合、外部配置するペイロードと WindowsApps 内に置くフットプリントファイルを整理する。
- マニフェストの `AllowExternalContent` と、インストール時の `-ExternalLocation` の両方が必要なことを確認する。
- 外部ペイロードの更新、アクセス制御、修復、アンインストールを既存インストーラーがどう担保するかを検証する。

## Visual Studio October Update – Compare Commits to Your Code, Resolve Conflicts in Bulk, Keep Coding

- **Blog:** Visual Studio
- **Author:** Mark Downie
- **URL:** https://devblogs.microsoft.com/visualstudio/visual-studio-october-update-compare-commits-to-your-code-resolve-conflicts-in-bulk-keep-coding

### 要約
Visual Studio 2026 Stable Channel の 10 月更新では、過去のコミットと現在の作業ツリーを比較する機能や、複数ファイルの競合をまとめて解決する機能が追加されました。新しい Copilot Chat 体験、未保存の作業を再起動後に復元する Hot Exit、タブ移動ショートカット、検索とプレビューを備えた Fonts and Colors 設定画面も紹介されています。

### 開発者にとって重要なこと
複数コミットにまたがる変更のレビューや、多数の競合解決にかかる手間を減らせます。Copilot Chat の新体験と Hot Exit は既定で有効ではなく、設定変更が必要です。タブ移動ショートカットの既定割り当ては従来のエディター操作と競合する可能性があるため、既存のキーバインドも確認が必要です。

### アクションプラン
- Visual Studio 2026 Stable Channel に更新し、Git Repository のコミットメニューから **Compare with Working Tree** を試す。
- 競合時に複数ファイルで同じ側を採用するケースでは、Git Changes の **Keep All Current** / **Take All Incoming** を確認し、適用対象を慎重に選ぶ。
- 新しい Copilot Chat を試す場合は **Tools > Options > GitHub > Copilot > Copilot Chat** で有効化し、再起動して動作を評価する。
- 未保存ファイルをセッション間で保持したい場合は Hot Exit を有効にする。タブ移動ショートカットを使う場合は、既存のキー割り当ても確認する。

### リファレンス
- [Visual Studio October Update – Compare Commits to Your Code, Resolve Conflicts in Bulk, Keep Coding](https://devblogs.microsoft.com/visualstudio/visual-studio-october-update-compare-commits-to-your-code-resolve-conflicts-in-bulk-keep-coding)

## Blazor Welcomes Open-Source Contributions from Infragistics

- **Blog:** .NET
- **Author:** Daniel Roth
- **URL:** https://devblogs.microsoft.com/dotnet/blazor-welcomes-infragistics

### 要約
Infragistics が Blazor の開発に参加し、50 種類以上のコントロールを MIT ライセンスのオープンソースとして公開しました。入力、ナビゲーション、レイアウト用の Ignite UI for Blazor コンポーネントに加え、Grid Lite 用の別パッケージも提供されます。Infragistics は .NET 11 向け Blazor アナライザーを ASP.NET Core に提供しており、セットアップ用スキャフォルダーは .NET のスキャフォールディングツールでレビュー中です。

### 開発者にとって重要なこと
商用アプリにも利用できるオープンソースの Blazor UI 部品が選択肢に加わり、アナライザーの改善は特定の UI ライブラリを使わない開発者にも役立ちます。Blazor Web Apps で Ignite UI を使うには対話型レンダーモードが必要で、サービス登録、名前空間、テーマなどの設定も必要です。

### アクションプラン
- 必要なコントロールがある場合は Ignite UI for Blazor のオープンソース一覧と MIT ライセンスを確認し、既存アプリで評価する。
- コアコントロールは `IgniteUI.Blazor.Lite`、Grid Lite は `IgniteUI.Blazor.GridLite` として別々に導入要否を判断する。
- 本番採用前に、アプリのレンダーモード、アクセシビリティ、パフォーマンス、セキュリティ、トリミング要件を評価し、公式のセットアップ手順に従う。
- スキャフォルダーは記事時点でレビュー中のため、利用可能になったかをリポジトリで確認する。

### リファレンス
- [Blazor Welcomes Open-Source Contributions from Infragistics](https://devblogs.microsoft.com/dotnet/blazor-welcomes-infragistics)

## Why don’t we run the taskbar and Task Manager at high priority, so they can remain responsive?

- **Blog:** The Old New Thing
- **Author:** Raymond Chen
- **URL:** https://devblogs.microsoft.com/oldnewthing/20261027-00/?p=112800

### 要約
CPU が逼迫したときにタスクバーや Task Manager を高優先度で動かしても、常に応答性を確保できるわけではない理由を説明しています。高優先度のスレッドも共有リソースの解放を待つ必要があり、UI スレッドやネットワークアクセスなど、優先度だけでは解消できない待ちが発生し得ます。Windows はフォーカス中のプログラムを優遇しますが、共有リソース上のブロックまでは防げません。

### 開発者にとって重要なこと
高いスレッド優先度だけで応答性を保証する設計はできず、共有ロックや UI 呼び出しなどの依存関係も考慮する必要があります。また、システム全体が過負荷のときは、問題を調査・解決するためのツール自体も影響を受ける可能性があります。

### アクションプラン
- アプリの応答性を調査するときは、CPU 使用率だけでなく、共有リソース待ち、ロック競合、UI スレッドのブロックも確認する。
- 高優先度化を回避策として安易に使わず、優先度逆転や長時間の I/O 待ちを含むスレッド間依存を検証する。

## Inspecting Local Data with Azure Cosmos DB Shell

- **Blog:** Cosmos DB
- **Author:** Jay Gordon
- **URL:** https://devblogs.microsoft.com/cosmosdb/inspecting-local-data-with-azure-cosmos-db-shell

### 要約
Azure Cosmos DB Shell と Linux Emulator を組み合わせ、開発中のローカルデータをターミナルから一覧、クエリ、ポイント読み取りで調べる手順を紹介しています。例では Docker 上の Emulator に FleetCharge のデータを投入し、データベースやコンテナーを移動しながら確認します。ポイント読み取りではアイテム ID に加えてパーティションキーが必要で、記事の例では .NET 10 以降の SDK を使うグローバルツール、または自己完結型バイナリから Shell を利用できます。

### 開発者にとって重要なこと
アプリのコードに一時的な診断 API を追加せず、ローカル開発・テスト環境で実際に保存されたデータを調べられます。これは本番インシデント調査や既存の CI テストの代替ではなく、開発中の確認手段です。シード処理は既存のローカル設定やデータに影響し得るため、接続先を明示して使う必要があります。

### アクションプラン
- Cosmos DB Emulator を使う開発者は、Shell のインストール方法と Emulator の接続先を確認し、ローカル環境で試す。
- `ls` での一覧は件数を制限し、対象を絞るクエリやポイント読み取りを使う。ポイント読み取りではアイテム ID と完全なパーティションキーの両方を指定する。
- シードデータを投入する場合は、ローカル Emulator の接続先・データベースを明示し、既存データを上書きしないか確認する。
- Shell の手動確認は既存 CI のテストを置き換えるものではないため、CI の検証は従来どおり維持する。

### リファレンス
- [Inspecting Local Data with Azure Cosmos DB Shell](https://devblogs.microsoft.com/cosmosdb/inspecting-local-data-with-azure-cosmos-db-shell)
