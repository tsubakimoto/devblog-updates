## MSVC Build Tools Version 14.52 Release Candidate Now Available

- **Blog:** C++ Team Blog
- **Author:** Eric Brumer
- **URL:** https://devblogs.microsoft.com/cppblog/msvc-build-tools-version-14-52-release-candidate-now-available

### 要約
MSVC Build Tools 14.52 のリリース候補版が Visual Studio 2026 Insiders Channel で公開され、C++23 が `/std:c++23` で本番利用可能になりました。コンパイラ、標準ライブラリ、リンカーや最適化の改善も含まれます。`/std:c++23preview` は引き続き使えますが、将来削除予定の非推奨エイリアスです。安定版は 11 月、Visual Studio 18.12 とともに提供予定です。

### 開発者にとって重要なこと
Insiders Channel で MSVC を試す C++ チームは、C++23 への移行や新しいコンパイラ動作を本番コードに近い条件で検証できます。一方、リリース候補版のため、現行の安定ツールセットと同一とは限らず、コンパイラ更新による警告・コード生成の変化も確認が必要です。

### アクションプラン
- Visual Studio 2026 Insiders Channel の C++ ワークロードで 14.52 RC を導入し、主要なビルド、テスト、対象アーキテクチャを検証する。
- C++23 を採用するプロジェクトは `/std:c++23` でビルドし、`/std:c++23preview` の使用箇所を置き換える計画を立てる。
- 問題があれば Visual Studio Developer Community に報告し、安定版移行前に影響を評価する。

### リファレンス
- [MSVC Build Tools Version 14.52 Release Candidate Now Available](https://devblogs.microsoft.com/cppblog/msvc-build-tools-version-14-52-release-candidate-now-available)

## Introducing dotnetup: A toolchain manager for .NET

- **Blog:** .NET
- **Author:** Chet Husk
- **URL:** https://devblogs.microsoft.com/dotnet/introducing-dotnetup

### 要約
macOS と Linux 向けに、ユーザー領域で .NET SDK とランタイムをインストール・管理する `dotnetup` のパブリックプレビューが発表されました。複数バージョンやプレビュー／日次ビルドを並行管理でき、`global.json` によるプロジェクトのバージョン固定にも対応します。管理者権限を必要とせず、CI でも利用できます。

### 開発者にとって重要なこと
開発マシンや一時的な CI 環境で、システム全体のインストールに依存せず SDK・ランタイムを揃えやすくなります。プレビュー段階のツールなので、既存の SDK 管理手順との併用や、シェル初期化・パス設定をチーム単位で評価してから採用するのが適切です。

### アクションプラン
- macOS／Linux の開発環境または隔離した CI ジョブで `dotnetup` を試し、既存の `global.json` と SDK 選択が期待どおり動くか確認する。
- SDK・ランタイムの追跡チャネル、更新、不要バージョンの削除が現在のチーム運用に合うか評価する。
- ⚠️ プレビュー版として開発・CI の限定環境で検証し、既存のシステムインストールや配布済みアプリのランタイム更新と混同しない。自己完結型アプリは更新ランタイムで再発行・再配布が必要。

### リファレンス
- [Introducing dotnetup: A toolchain manager for .NET](https://devblogs.microsoft.com/dotnet/introducing-dotnetup)

## Stop waiting on a failed build

- **Blog:** Visual Studio Blog
- **Author:** Mads Kristensen
- **URL:** https://devblogs.microsoft.com/visualstudio/stop-waiting-on-a-failed-build

### 要約
Visual Studio 2026 バージョン 18.11 に、プロジェクトのビルドが最初に失敗した時点でソリューションビルドを停止するオプションが追加されました。**Tools > Options > Projects and Solutions > Build and Run** から有効化でき、実行中・待機中の後続プロジェクトも停止します。記事の 4 回のテストでは失敗後の完了待ちが平均 26 秒から 1.5 秒に短縮されましたが、成功ビルドが速くなるという意味ではありません。

### 開発者にとって重要なこと
最初のエラーを直して再ビルドする開発者は、失敗後に不要なビルド完了を待つ時間を減らせます。一方、この設定は失敗したプロジェクトに依存するものだけでなくソリューション内の後続ビルド全体を止めるため、残りのプロジェクトの診断結果も集めたい場合には無効のままが適しています。

### アクションプラン
- 失敗後に手動でビルドを中断することが多いソリューションでオプションを有効化し、通常のトラブルシューティングに合うか試す。
- 他プロジェクトのビルド結果も必要なチームでは、既定の継続動作を維持するか、用途に応じて設定を切り替える。

### リファレンス
- [Stop waiting on a failed build](https://devblogs.microsoft.com/visualstudio/stop-waiting-on-a-failed-build)

## C++ futures part 4: What if I want an immediate on-thread std::async ?

- **Blog:** The Old New Thing
- **Author:** Raymond Chen
- **URL:** https://devblogs.microsoft.com/oldnewthing/20261015-00/?p=112776

### 要約
`std::async` には呼び出し元スレッドで直ちに実行する指定がないため、同期実行しつつ `std::future` が必要な場合の代替方法を紹介しています。`std::promise` に結果または例外を設定する方法、`std::packaged_task` を直接実行する方法、`std::launch::deferred` で作った future をすぐ `wait()` する方法が示されています。

### 開発者にとって重要なこと
同期的な処理を future ベースの API に渡す必要がある C++ 開発者に関係します。単に同期関数を呼べばよい場合まで future 化する必要はなく、future を要求するインターフェイスとの接続に限って選択肢を検討できます。

### アクションプラン
- 呼び出し先が `std::future` を要求している理由を確認し、同期関数呼び出しで十分なら複雑さを増やさない。
- 同期結果を future に包む必要がある場合は、例外伝播を含めて `promise` または `packaged_task` の実装を検証する。
- `deferred` を使う場合は、`wait()`／`get()` などで遅延処理を実際に実行することを確認する。

### リファレンス
- [C++ futures part 4: What if I want an immediate on-thread std::async ?](https://devblogs.microsoft.com/oldnewthing/20261015-00/?p=112776)

## AI Agents: Meet the Azure Cosmos DB vNext Emulator

- **Blog:** Azure Cosmos DB Blog
- **Author:** Theo van Kraay
- **URL:** https://devblogs.microsoft.com/cosmosdb/ai-agents-meet-the-azure-cosmos-db-vnext-emulator

### 要約
Azure Cosmos DB vNext Emulator を、コーディングエージェントがデータベースを起動し、テストデータを準備し、アプリを実行・診断するローカル開発ループに活用する方法を紹介しています。Linux コンテナーとして Windows、macOS、Linux の x64／ARM64 ホストで動作し、シェル、初期化スクリプト、OTLP トレース、バイナリプロトコル対応などがエージェントの作業を支援します。vNext は GA ですが、従来版エミュレーターからの移行が完了したという意味ではありません。

### 開発者にとって重要なこと
エージェントを含む開発・テスト環境で、破棄可能な Cosmos DB ローカル環境を利用したいチームに有用です。ただしエミュレーターはクラウド機能すべての再現を保証せず、認証も強制されません。ローカル統合テストは Azure 上での検証の代わりにはなりません。

### アクションプラン
- Docker を利用できる開発環境で vNext を起動し、既存の統合テスト、初期データ投入、診断フローを試す。
- CI では `vnext-latest` に固定せず、検証済みのリリースまたはイメージ digest を指定する。
- ⚠️ エミュレーターを隔離されたローカル／CI 環境に限定し、認証・本番相当の互換性が必要な検証は Azure でも実施する。

## Canada’s 2026 time zone updates: guidance for Microsoft SQL

- **Blog:** Azure SQL Blog
- **Author:** Umachandar Jayachandran (UC)
- **URL:** https://devblogs.microsoft.com/azure-sql/canadas-2026-time-zone-updates-guidance-for-microsoft-sql

### 要約
ブリティッシュコロンビア州の大部分、アルバータ州およびマニトバ州の対象地域では、2026 年 11 月 1 日に時計を戻さず、それぞれ UTC−07:00、UTC−06:00、UTC−05:00 に留まる予定です。新しい地域タイムゾーンが SQL 環境で利用できるまでの暫定設定として、対象地域ごとに Yukon Standard Time、Canada Central Standard Time、Eastern Standard Time (Mexico) を使う方法を説明しています。SQL Server on Windows は適用される Windows 更新を必要とし、Azure SQL Managed Instance のインスタンス単位のタイムゾーンは既存インスタンスで変更できません。

### 開発者にとって重要なこと
対象地域の現地時刻を使う SQL Server、Azure SQL Database、Managed Instance の運用者は、スケジュール、現在時刻関数、明示的な `AT TIME ZONE` 変換への影響を確認する必要があります。暫定 ID は必要な現在・将来のオフセットに合わせたもので、地域の完全な過去のタイムゾーン規則を再現するものではありません。また、州全域へ一律適用できない地域区分や、製品ごとの設定差があります。

### アクションプラン
- 対象サーバー、データベース、セッション、SQL Agent ジョブ、アプリの明示的なタイムゾーン変換を棚卸しし、所在地別に影響を判定する。
- SQL Server on Windows は該当する Windows 更新を適用する。Linux は SQL Server プロセスに反映される `TZ` と SQL タイムゾーン ID の対応を確認し、Azure SQL は製品・機能の対応範囲に沿って設定する。
- ⚠️ 暫定 ID を過去データの一括変換に使わず、`sys.time_zone_info` で対象環境の利用可否を確認する。新しい地域 ID が使えるようになった後の切り替え方法と、Managed Instance の場合は必要な移行・停止時間も計画する。

### リファレンス
