## Code with Cosmos: Build a Production-Ready AI App in Four Episodes

- **Blog:** Cosmosdb
- **Author:** Azure Cosmos DB Team
- **URL:** https://devblogs.microsoft.com/cosmosdb/code-with-cosmos

### 要約
Azure Cosmos DB を使い、AI 旅行プランナーを試作品から本番運用を見据えたマルチエージェントアプリへ発展させる全4回の動画シリーズが紹介されています。ローカルでの開発から、運用データとベクトル・全文・ハイブリッド検索の利用、エージェント間で共有する永続メモリ、トレースや評価・回帰テストによる運用改善までを段階的に扱います。

### 開発者にとって重要なこと
AI アプリを回答生成だけの試作で終わらせず、最新データ、トランザクション、セッションをまたぐ状態、複数エージェントの連携、運用時の可観測性まで設計する際の具体例になります。シリーズではローカルの Cosmos DB Emulator を使った開発も紹介されており、初期構築に Azure サブスクリプションを必要としない進め方を確認できます。

### アクションプラン
- アプリで必要なデータ検索、予約などの処理、会話をまたぐ記憶、エージェント間の引き継ぎを整理し、4回の動画で対応する設計例を確認する。
- Azure Cosmos DB を検討する場合は、[サンプルリポジトリ](https://aka.ms/cosmos-travel-planner)を使ってローカル開発から小規模に試し、検索方式やデータモデルが要件に合うか評価する。
- 本番運用を想定するチームは、トレース、評価、回帰テストを使った検索品質・レイテンシ・トークン量・要求ユニットの計測方法を確認する。

### リファレンス
- [Code with Cosmos: Build a Production-Ready AI App in Four Episodes](https://devblogs.microsoft.com/cosmosdb/code-with-cosmos)

## Why didn’t we use the COM static store to clean up the unmarshalable delegate?

- **Blog:** The Old New Thing
- **Author:** Raymond Chen
- **URL:** https://devblogs.microsoft.com/oldnewthing/20261023-00/?p=112793

### 要約
アンマーシャリングできないデリゲートを片付けるために COM static store を使う案が適さない理由を説明しています。通常の COM static store は最後の COM スレッドが終了すると片付けられるため、単一アパートメントの終了時に片付けたい用途とは寿命が一致しません。アパートメント単位のストアは UWP の `CoreApplicationView` に限られ、キーの生成・管理も必要になるうえ、Global Interface Table のインデックス参照より操作の負荷が大きくなります。

### 開発者にとって重要なこと
COM オブジェクトやデリゲートの寿命をアパートメントに結び付ける設計では、スレッド単位の終了処理とアパートメント単位の終了処理を区別する必要があります。利用可能なストアの適用範囲や、追加のキー管理・検索コストも選択に影響します。

### アクションプラン
- COM リソースのクリーンアップを設計・調査する際は、必要な寿命がスレッド単位かアパートメント単位かを明確にし、COM static store の終了条件と照合する。
- `CoreApplicationView` を使う案は、UWP かつ対象のアパートメントがコアアプリケーションビューを持つ場合に限られることを確認する。
- 代替案を比較する場合は、キーの生成・削除管理を含む実装コストと Global Interface Table の参照コストを考慮する。

## From Local Development to CI Workflows with the Azure Cosmos DB Emulator

- **Blog:** Cosmosdb
- **Author:** Jay Gordon
- **URL:** https://devblogs.microsoft.com/cosmosdb/from-local-development-to-ci-workflows-with-the-azure-cosmos-db-emulator

### 要約
Azure Cosmos DB Emulator を Docker でローカル起動し、実際の SDK を使ったデータベース連携テストを開発環境から GitHub Actions の CI へつなぐ方法を、FleetCharge のデモアプリで紹介しています。単に HTTP 200 を確認するだけでなく、書き込みが保存され、アプリが更新後のデータを読み取って応答に反映することを検証します。記事中の FleetCharge はデモアプリであり、本番向けではありません。

### 開発者にとって重要なこと
Cosmos DB を使うアプリでは、API の応答確認だけではデータ永続化や読み取り後の動作を保証できません。ローカルと CI で新しい Emulator を使うテストを実行すれば、Azure アカウントに依存せず、PR ごとにデータベース操作を含む検証を再現できます。

### アクションプラン
- Cosmos DB を使うアプリでは Emulator と本番 SDK を用いたテストを試し、書き込み後に保存データを読み取り、アプリの結果へ反映されることまで検証する。
- CI へ導入する場合は、記事のサンプルを参考に PR ごとに分離した Emulator を起動し、準備完了後にテストを実行して終了時に片付ける。
- 導入前に Python 3.12、Docker の Linux コンテナーなど記事の前提条件を確認する。サンプルアプリはデモ用途であり、本番サービスとして利用しない。
- Emulator のポートはローカルのループバックに限定し、記事の CI 設定やサンプルリポジトリを自分のプロジェクトへ取り込む際は環境・依存関係を確認する。

### リファレンス
- [From Local Development to CI Workflows with the Azure Cosmos DB Emulator](https://devblogs.microsoft.com/cosmosdb/from-local-development-to-ci-workflows-with-the-azure-cosmos-db-emulator)
