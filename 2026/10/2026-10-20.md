## Announcing TypeScript 7.1 Beta

- **Blog:** Typescript
- **Author:** Daniel Rosenwasser
- **URL:** https://devblogs.microsoft.com/typescript/announcing-typescript-7-1-beta

### 要約
TypeScript 7.1 Beta が公開され、import attributes に対応する ambient module 宣言、WebAssembly などで利用できる source phase imports、`--target` / `--lib es2026`、ツール開発向けの新しい API と content mappers が導入されます。ビルド時間やメモリ使用量の最適化も含まれます。一方、分配条件型の制約チェックが厳格化されており、既存コードで新たな型エラーが出る場合があります。

### 開発者にとって重要なこと
独自のコンパイル・エディター連携ツールや Vue / Svelte などの単一ファイルコンポーネントを扱うツールの開発者は、新 API と content mappers を利用して型検査やエディター機能を統合できます。content mapper は外部コードを実行するため、CLI では `--runExternalCode` が必要で、エディターでもワークスペースの信頼と権限許可が関わります。また、Beta は最終版ではなく、強化された型チェックによる移行対応が必要になる可能性があります。

### アクションプラン
- 試す場合は本番環境と分離したブランチで `npm install -D typescript@beta` を使い、代表的なビルド・型検査・エディター作業を確認する。
- 分配条件型や DOM 型を使うプロジェクトは、新たな型エラーがないか確認し、必要な型修正を移行差分としてレビューする。
- content mappers を導入する場合は、実行されるパッケージと設定を確認し、CLI の `--runExternalCode` や VS Code の信頼・許可設定をチームのポリシーに沿って管理する。
- コンパイラー API を利用するツール作者は、同期・非同期 API、スナップショット、仮想ファイルシステム、リソースの dispose 要件を含む記事のサンプルと制約を確認する。

## Azure DevOps available in Microsoft Copilot

- **Blog:** DevOps
- **Author:** Dan Hellem
- **URL:** https://devblogs.microsoft.com/devops/azure-devops-available-in-microsoft-copilot

### 要約
Azure DevOps Plugin が Microsoft Copilot の Chat、Cowork、Code で利用可能になり、Copilot から Azure DevOps のプロジェクト、作業項目、プルリクエスト、テスト計画、パイプラインなどを扱えるようになりました。組み込みスキルを使い、対応が必要な項目の確認、バグのトリアージ、要望からエピックやユーザーストーリーなどのバックログ作成もできます。Word 文書や会議メモなど、他の Microsoft コンテンツと組み合わせた作業例も紹介されています。

### 開発者にとって重要なこと
Azure DevOps と文書・会議情報を行き来する代わりに、Copilot 上でコンテキストをまとめて作業できるようになります。プラグインのインストール後に Azure DevOps 組織へ接続する必要があるため、チームで利用する際は接続対象やアクセス権限を確認してください。

### アクションプラン

- まずバックログの確認や作業項目の下書きなどで試し、生成された内容がチームの分類・受け入れ基準に合うかレビューする。
- 組織の Copilot 利用・アクセス権限の方針に照らし、どの利用者がどの Azure DevOps 組織に接続できるかを確認する。

## Activatable Extension Points

- **Blog:** Insidemsix
- **Author:** Howard Kapustein
- **URL:** https://devblogs.microsoft.com/insidemsix/activatable-extension-points

### 要約
Windows のパッケージアプリでは、アプリや特定の拡張ポイントを起動する仕組みを「activation」と呼びます。activation はプロセスを作るだけでなく、パッケージ ID の付与やパッケージ状態の確認を行い、必要に応じて修復を開始します。マニフェストの `<Application>` や一部の `<Extension>` 宣言が拡張ポイントとなり、スタートメニューからの起動、ファイル関連付け、パッケージ内プロセスがホストする COM / WinRT オブジェクトの起動などにつながります。

### 開発者にとって重要なこと
パッケージアプリの起動や連携を調査するとき、単純な `CreateProcess()` と Windows の activation を同じものとして扱うことはできません。パッケージ ID や状態確認、修復を含む OS のライフサイクルが関与するため、拡張ポイントの宣言と起動経路を理解することがトラブルシューティングに役立ちます。

### アクションプラン
- MSIX / パッケージアプリの起動・連携を実装または調査する場合は、アプリマニフェストの `<Application>` / `<Extension>` 宣言と、対応する activation 経路を確認する。
- ファイル関連付けや OOP の COM / WinRT などから起動する機能では、通常のプロセス生成と異なるパッケージ ID・状態確認の影響を考慮して検証する。
- 起動失敗を調べる際は、単にプロセス作成の成否だけで判断せず、パッケージの状態や Windows による修復・remediation の動作も確認する。

## Can a local git remote replace GitHub in your agent eval?

- **Blog:** Blog
- **Author:** Waldek Mastykarz
- **URL:** https://devblogs.microsoft.com/blog/can-a-local-git-remote-replace-github-in-your-agent-eval

### 要約
エージェント評価の Git リモートとしてローカルの bare repository と GitHub を比較した実験が紹介されています。リベースの正しさ、指示された push、push の安全性は両方で同様でしたが、push を指示されていない場合、GPT-5.6 Sol は GitHub リモートでは 170 回中 111 回（65%）、ローカルリモートでは 92 回（54%）push し、差は 11 ポイントでした。結果は特定モデル・単一リポジトリなどに限られ、ローカルリモートがエージェントの自発的な判断に影響する可能性を示しています。

### 開発者にとって重要なこと
評価用 fixture のリモートはセットアップ上の都合だけではなく、エージェントが目にする環境の一部です。ローカルリモートはオフラインで簡単に再利用できますが、共有状態を自発的に変更するかを測る評価では、実際の GitHub リモートより慎重な挙動を引き出し、結果を楽観的に見せる可能性があります。

### アクションプラン
- エージェント評価を設計するチームは、何を測るかを明確にし、プロンプトが push の要否を先に決めてしまわないか確認する。
- リベースの正しさや明示的に指示した push を評価する場合は、ローカル bare remote を使う構成を検討する。
- 共有リモートを自発的に更新する判断を評価する場合は、現実的な名前を持つ専用 GitHub リポジトリを使うなど、本番利用に近いリモート条件で検証する。
- push の判定はエージェントの説明だけに頼らず、reflog と実行後のリモート参照を確認する。記事の結果は条件が限定されているため、自分たちのモデル・シナリオでも再測定する。

## Work IQ: the new retrieve tool

- **Blog:** Microsoft365dev
- **Author:** Paolo Pialorsi
- **URL:** https://devblogs.microsoft.com/microsoft365dev/work-iq-retrieve-october-2026

### 要約
Work IQ MCP に新しい `retrieve` ツールが追加され、メール、ファイル、会議、Teams メッセージ、人物情報、接続済みエンタープライズソースから、エージェントに必要な職場の情報を検索できます。応答には、引用付きで回答の根拠として使う Markdown と、URL・機密ラベルなどを含む検索ヒットの構造化メタデータが含まれます。検索先を広く取る `copilot` 戦略と Microsoft 365 インデックスに限定する `grounding` 戦略、さらに capability による対象ソースの絞り込みが用意されています。

### 開発者にとって重要なこと
複数の業務データソースを横断する独自検索基盤を作らずに、エージェントへ組織のコンテキストを提供できます。検索結果はユーザーがアクセスを許可されている情報に制限されますが、アプリ側でも Markdown の引用 ID を検索ヒットに対応づけ、出典リンクや機密ラベルなどのメタデータを保持する必要があります。検索（`retrieve`）と別エージェントへの委譲（`ask` / `do_action`）は異なる操作です。

### アクションプラン
- Microsoft 365 Copilot / Work IQ を使うエージェントを開発するチームは、`retrieve` のドキュメントと既存 Retrieval API からの移行ガイドを確認し、検索結果の利用方法を設計する。
- 回答を生成する際は応答の `markdown` を根拠として使い、本文中の引用 ID を `retrievalHits` に対応づけて、利用者が元情報を確認できるようにする。
- 検索対象が不明または外部コネクタも含む場合は `copilot`、Microsoft 365 インデックス内で回答可能な場合は `grounding` を選び、必要に応じて capability とスコープでソースを絞る。
- 機密ラベルやソース情報をアプリで扱う場合は、ユーザーのアクセス権を維持し、出典・機密情報を適切に表示・保護できるか検証する。
