## Durable Task in the Real World: What Problems Does It Actually Solve?

- **Blog:** .NET
- **Author:** Tamir Dresher
- **URL:** https://devblogs.microsoft.com/dotnet/durable-task-in-the-real-world

### 要約
Durable Task が役立つ場面を、請求承認、Azure 環境のプロビジョニング、決済の照合、Webhook 処理、AI エージェントによるインシデント対応の例で解説しています。長時間の待機や中断後の再開を調整できる一方、外部システムの結果の正当性、重複実行への対処、安全なクリーンアップなどはアプリケーション側の責任として残ります。

### 開発者にとって重要なこと
人手の承認や外部サービスの処理をまたぐ長時間ワークフローでは、再開状態を独自実装する負担を減らせます。ただし、Durable Task は外部副作用の exactly-once 実行を保証しません。ARM のように既存サービスが依存関係や再試行を扱える場合は、Durable Task を追加しても利点が少ないことがあります。

### アクションプラン
- .NET の長時間ワークフローを洗い出し、既存のキュー、バックグラウンド処理、ARM で十分か、永続的な待機・再開が必要かを比較する。
- 導入する場合は、安定した操作 ID と冪等性、外部処理の照合、タイムアウト後の扱いを設計し、承認や決済などの確定情報はアプリケーションの権威あるストアで検証する。
- Azure リソースの補償処理では、進行中の操作と所有権を確認してから削除し、安全性を判断できない場合は自動削除せず介入を求める。
- AI エージェントでは、再実行時に提案を再生成して別の判断に置き換えないよう、承認対象の提案と実行結果を永続化する。具体例と制約は本文を参照。

## C++ futures part 1: The mental model

- **Blog:** The Old New Thing
- **Author:** Raymond Chen
- **URL:** https://devblogs.microsoft.com/oldnewthing/20261012-00/?p=112767/

### 要約
C++ の `std::promise`、`std::packaged_task`、`std::async`、`std::future` などを理解するため、結果を共有する内部状態の基本モデルを説明しています。その状態には値または例外が一度設定され、待機側は完了を待って結果を取得します。値を消費して以後取得できなくなる場合と、参照して取得する場合の違いも示しています。

### 開発者にとって重要なこと
非同期処理で値や例外がどのように producer から consumer へ渡るかを整理するための基礎知識です。`future` 系クラスの使い分けや、結果の取得が再度可能かどうかを考える際に、共有状態とその消費規則を意識できます。

### アクションプラン
- `promise` と `future` を使うコードで、値・例外を設定する側と待機・取得する側の責任、および結果を一度しか設定できない前提を確認する。
- `get()` による取得後の状態や、共有して複数箇所から参照する必要がある場合の型の選択を確認する。細かな仕様と続編の内容は本文を参照。
