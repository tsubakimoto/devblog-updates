## Is it MSIX? Part 3: Find Package and Application Identity with TASKLIST and PowerShell

- **Blog:** Insidemsix
- **Author:** Howard Kapustein
- **URL:** https://devblogs.microsoft.com/insidemsix/find-msix-package-application-identity

### 要約
MSIX 化されたプロセスのパッケージ ID は、`TASKLIST /APPS` と PID または実行ファイル名によるフィルターで確認できます。Application User Model ID は TASKLIST には表示されないため、記事では Windows のパッケージ照会 API を PowerShell から呼び出して取得する方法を紹介しています。

### 開発者にとって重要なこと
アプリの診断やサポート時に、実行中プロセスがどの MSIX パッケージとアプリ ID に属するかを、専用のネイティブツールを作らず調べられます。

### アクションプラン
- 対象プロセスを調査するときは `TASKLIST /APPS /FI "PID eq <PID>"` または `IMAGENAME` フィルターでパッケージ名を確認する。
- AUMID も必要な診断手順では、記事の PowerShell 例を確認し、組織の実行ポリシーやプロセス権限に沿って利用する。

### リファレンス
- [Is it MSIX? Part 3: Find Package and Application Identity with TASKLIST and PowerShell](https://devblogs.microsoft.com/insidemsix/find-msix-package-application-identity)

## Azure Content Understanding Prebuilt Analyzers: packaging domain knowledge for document AI

- **Blog:** Foundry
- **Author:** Chu Lahlou
- **URL:** https://devblogs.microsoft.com/foundry/more-than-a-schema-content-understanding-prebuilt-analyzers

### 要約
Azure Content Understanding の事前構築済みアナライザーは、請求書、税務書類、身分証明書などに対し、スキーマだけでなく文書種別に関する知識を組み合わせて構造化データを抽出します。対応フィールドでは、型付き・正規化済みの値に加えて信頼度や文書内の根拠位置を返し、曖昧な結果のレビューや業務ルールによる検証に利用できます。

### 開発者にとって重要なこと
一般的な抽出スキーマだけでは判別しにくい金額の意味、項目間の関係、地域ごとの表記などを扱いやすくし、文書処理の初期実装に役立ちます。ただし、業務固有のルールや人手確認が不要になるわけではありません。

### アクションプラン
- 処理対象の文書種別がカタログにある場合は、独自アナライザーを作る前に事前構築済みアナライザーを評価する。
- 実データで値の正確さと根拠位置を検証し、信頼度に応じた自動処理・人手レビューの基準と業務ルールを設計する。
- 対応文書種別や出力フィールド、組み合わせ可能なアナライザーの詳細は本文とドキュメントを参照する。

### リファレンス
- [Azure Content Understanding Prebuilt Analyzers: packaging domain knowledge for document AI](https://devblogs.microsoft.com/foundry/more-than-a-schema-content-understanding-prebuilt-analyzers)

## C++ futures part 2: The mental model for std::promise , std::packaged_task

- **Blog:** The Old New Thing
- **Author:** Raymond Chen
- **URL:** https://devblogs.microsoft.com/oldnewthing/20261013-00/?p=112769/

### 要約
C++ の `std::promise` や `std::packaged_task` が、前回説明された共有状態（記事中の `source`）をどのように使うかを解説しています。`packaged_task` は呼び出し可能オブジェクトを保持し、実行結果または例外を共有状態に格納するため、対応する `future` から後で取得できます。

### 開発者にとって重要なこと
非同期処理で処理を実行する側と結果を受け取る側がどう接続されるかを理解する助けになります。特に `packaged_task` が callable の結果や例外を `future` に渡す仕組みを把握すると、既存の非同期コードの設計やデバッグに役立ちます。

### アクションプラン
- `packaged_task` を使うコードで、タスクの起動、`get_future()` による結果の受け渡し、値または例外の伝播を確認する。
- `std::promise` と `std::packaged_task` の責任範囲や `std::async` との違いは、本文および続編を参照する。

## Build AI-powered apps without creating a vector database

- **Blog:** Microsoft365dev
- **Author:** Steve Pucelik
- **URL:** https://devblogs.microsoft.com/microsoft365dev/build-ai-powered-apps-without-creating-a-vector-database

### 要約
SharePoint Embedded のコンテンツを AI アプリの根拠情報として使う方法として、Microsoft 365 Copilot Retrieval API と SharePoint Embedded MCP サーバー（パブリックプレビュー）が紹介されています。Retrieval API は関連テキストをユーザーの権限に合わせて返し、アプリ側でプロンプトやモデルを制御しながら、独自のベクトルデータベースや権限同期基盤を構築せずに済む構成を支援します。

### 開発者にとって重要なこと
SharePoint Embedded を使うアプリでは、コンテンツと Microsoft Purview などのガバナンスを Microsoft 365 テナント内に保ちながら、独自の AI 体験を構築できます。従量課金の方式や Copilot ライセンスの条件、MCP サーバーがプレビューである点を導入前に確認する必要があります。

### アクションプラン
- SharePoint Embedded のコンテンツを使う AI アプリでは、Retrieval API と Foundry の SharePoint ナレッジソースのどちらが要件に合うか比較する。
- 検索結果の権限、テナントのコンプライアンス要件、課金方式、ライセンス条件を検証し、独自の検索基盤を運用する場合と比較する。
- MCP サーバーを試す場合はプレビュー機能として開発・検証環境で評価し、対応シナリオと制約をドキュメントで確認する。

### リファレンス
- [Build AI-powered apps without creating a vector database](https://devblogs.microsoft.com/microsoft365dev/build-ai-powered-apps-without-creating-a-vector-database)

## WinUI Gallery 3.0 is here: TableView, Charts, InkCanvas and more

- **Blog:** Ifdef Windows
- **Author:** Niels Laute
- **URL:** https://devblogs.microsoft.com/ifdef-windows/winui-gallery-3-0-is-here-tableview-charts-inkcanvas-and-more

### 要約
WinUI Gallery 3.0 は、実験的な Windows App SDK（現行記事記載の 2.5.4-experimental）を同梱し、新しい WinUI API のサンプルを安定版より早く試せるようになりました。TableView、Charts、WrapPanel、PagerControl、InkCanvas、ウィンドウサイズ設定 API などの実験的なサンプルに加え、検索やナビゲーションも改善されています。

### 開発者にとって重要なこと
WinUI 3 開発者は、今後のコントロールや API を実際のサンプルで試し、安定版になる前にフィードバックできます。一方、実験的 API は変更・削除される可能性があり、本番アプリでの利用は避けるよう明記されています。

### アクションプラン
- 新しい WinUI コントロールを評価する際は Gallery 3.0 の実験的サンプルと生成される XAML/C# を確認する。
- 実験的機能は検証環境に限定し、本番採用は安定版への移行と API の確定を待つ。
- 利用中の WinUI 開発チームはサンプルを試し、必要に応じて実験段階でフィードバックする。
