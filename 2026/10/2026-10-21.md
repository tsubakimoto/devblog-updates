## Microsoft.UI.Reactor: a C#-first way to build WinUI apps

- **Blog:** Ifdef Windows
- **Author:** Alexandre Zollinger Chohfi
- **URL:** https://devblogs.microsoft.com/ifdef-windows/microsoft-ui-reactor-a-c-first-way-to-build-winui-apps

### 要約
Microsoft.UI.Reactor は、WinUI の実際のコントロールを使いながら、C# で MVU（Model-View-Update）パターンの UI を記述する実験的なフレームワークです。XAML・コードビハインド・ViewModel を使わずに UI を表現できますが、サポートポリシーや API 保証はなく、XAML や MVVM の置き換えを目指すものではありません。

### 開発者にとって重要なこと
WinUI で C# 中心の UI や MVU に関心があるチームにとって、新しい設計を試す材料になります。一方、実験段階のため、本番アプリの基盤として採用すると API 変更やサポート面のリスクがあります。

### アクションプラン
- WinUI アプリで MVU を試したい場合は、既存アプリと分離したサンプルで Reactor の記述方法と既存 WinUI コントロールとの連携を評価する。
- 採用を検討する場合は、実験的で API 保証がない点を踏まえ、本番利用の判断を保留し、リポジトリと記事で最新の制約を確認する。

### リファレンス
- [Microsoft.UI.Reactor: a C#-first way to build WinUI apps](https://devblogs.microsoft.com/ifdef-windows/microsoft-ui-reactor-a-c-first-way-to-build-winui-apps)

## Why didn’t we use RoRegisterForApartmentShutdown to clean up the unmarshalable delegate?

- **Blog:** The Old New Thing
- **Author:** Raymond Chen
- **URL:** https://devblogs.microsoft.com/oldnewthing/20261021-00/?p=112786

### 要約
非 marshalable な delegate をアパートメント終了時に解放する方法として `RoRegisterForApartmentShutdown` が適さない理由を解説しています。登録対象には agile オブジェクトが必要で、終了コールバック中の登録解除は禁止されており、さらに登録解除は登録したアパートメントから行う必要があります。

### 開発者にとって重要なこと
COM / WinRT のアパートメント境界をまたぐラッパーやオブジェクトの寿命管理では、単に shutdown コールバックに解放処理を移すだけでは安全性を確保できません。登録解除の制約や、ラッパー自身が抱える非 agile オブジェクトの解放場所を考慮する必要があります。

### アクションプラン
- COM / WinRT オブジェクトのクリーンアップを実装する場合は、`RoRegisterForApartmentShutdown` の agile 要件、コールバック内での登録解除禁止、同一アパートメント要件を確認する。
- agile wrapper を設計する際は、内部の非 agile オブジェクトが誤ったアパートメントで解放されないか、終了時の参照関係も含めて検証する。

### リファレンス
- [Why didn’t we use RoRegisterForApartmentShutdown to clean up the unmarshalable delegate?](https://devblogs.microsoft.com/oldnewthing/20261021-00/?p=112786)
