## Bringing rich terminal experiences to Aspire

- **Blog:** Aspire
- **Author:** Mitch Denny
- **URL:** https://devblogs.microsoft.com/aspire/aspire-terminal-support

### 要約
Aspire 13.5 で、プロジェクト、実行可能ファイル、コンテナーに `WithTerminal()` / `withTerminal()` を付け、ダッシュボードから対話型のターミナルを利用できるようになりました。Aspire 13.6 ではドッキング、REPL、`aspire terminal attach`、Tape ファイルによる自動化などが追加され、tmux、Kitty Graphics Protocol、Sixels にも対応します。

### 開発者にとって重要なこと
対話型コンソールを持つアプリやデータベースの REPL を、別の端末へ接続設定を移さず Aspire の開発体験に統合できます。ターミナル API と `aspire terminal` コマンドは実験的なため、開発環境の利便性を高める一方で、将来の API 変更を織り込む必要があります。

### アクションプラン
- Aspire 開発チームは 13.5 以降へ更新し、対話型リソースに `.WithTerminal()`、対応する Redis などのリソースに `.WithRepl()` を追加して検証する。
- カスタムリソースでは `TerminalService`、外部端末からは `aspire terminal attach`、再現可能な操作では Tape ファイルを試し、既存の開発・テスト手順への適合性を確認する。
- ⚠️ 実験的 API とコマンドのため、固定バージョンで検証し、将来の Aspire 更新時にコードと自動化スクリプトを再確認する。

### リファレンス
- [Bringing rich terminal experiences to Aspire](https://devblogs.microsoft.com/aspire/aspire-terminal-support)

## Genspark protects live agent sessions with Azure Cosmos DB Global Secondary Indexes

- **Blog:** Cosmosdb
- **Author:** Azure Cosmos DB Team
- **URL:** https://devblogs.microsoft.com/cosmosdb/genspark-protects-live-agent-sessions-with-azure-cosmos-db-global-secondary-indexes

### 要約
Genspark は、AI エージェントのライブセッションと読み取り負荷の高いバックグラウンド処理が同じ容量を消費する課題に対し、Azure Cosmos DB Global Secondary Indexes (GSI) を利用しました。ライブの読み書きはソースコンテナーに残し、遅延を許容できるバックグラウンド処理を GSI へ振り分け、変更フィードによる同期で別のレプリケーション基盤を運用せずにワークロードを分離しています。

### 開発者にとって重要なこと
エージェントの状態管理など、急増しやすいライブトラフィックと内部集計・検索を同じ Cosmos DB で処理するチームに適用できる設計例です。GSI は結果整合性であるため、最新状態が必須の処理と、多少古いデータでも安全な処理を明確に分けることが成功条件になります。

### アクションプラン
- Azure Cosmos DB チームは、ライブ処理とバックグラウンド処理の読み取りを棚卸しし、「データが遅れていたら何が壊れるか」を基準に GSI へ移せる処理を分類する。
- 小さな対象から GSI を構成し、同期遅延がある場合と追いついている場合の両方で、結果の正しさ、RU 消費、ライブセッションのレイテンシーを測定する。
- 最新状態が必要な読み取りはソースコンテナーに残し、GSI の整合性モデルと運用監視を設計書・障害対応手順に明記する。

### リファレンス
- [Genspark protects live agent sessions with Azure Cosmos DB Global Secondary Indexes](https://devblogs.microsoft.com/cosmosdb/genspark-protects-live-agent-sessions-with-azure-cosmos-db-global-secondary-indexes)

## Azure Cosmos DB Shell is now available in the Azure portal

- **Blog:** Cosmosdb
- **Author:** Sajeetharan Sinnathurai
- **URL:** https://devblogs.microsoft.com/cosmosdb/azure-cosmos-db-shell-is-now-available-in-the-azure-portal

### 要約
Azure portal の Azure Cosmos DB for NoSQL の Data Explorer から、接続済みの Azure Cosmos DB Shell を新しいタブで直接開けるようになりました。`ls`、`cd`、`pwd` による移動、NoSQL クエリ、設定・スキーマ・権限の確認、項目の作成・更新・削除、変数やスクリプトを使った反復操作に対応します。

### 開発者にとって重要なこと
エンドポイントや接続文字列を別ツールへコピーせず、ポータルで確認しているアカウントのデータを調査・検証できます。対象環境での診断や小さな変更を素早く行える一方、項目の更新・削除も可能なため、権限と変更管理を伴う運用が必要です。

### アクションプラン
- Cosmos DB 運用チームは Data Explorer から **Open Cosmos DB Shell** を開き、`info`、`schema`、`whoami`、`can-i` を使った読み取り中心の調査フローを検証する。
- 変更操作を行う場合は対象アカウント、コンテナー、資格情報、監査要件を確認し、本番環境では最小権限と承認手順を適用する。
- ⚠️ 現在はプレビューでコマンド、出力、動作が変わる可能性があるため、再利用する操作はスタンドアロン Shell のスクリプトや手順として別途検証する。

### リファレンス
- [Azure Cosmos DB Shell is now available in the Azure portal](https://devblogs.microsoft.com/cosmosdb/azure-cosmos-db-shell-is-now-available-in-the-azure-portal)

## Windows on Itanium also provided for hot-patching, in an even simpler way

- **Blog:** Oldnewthing
- **Author:** Raymond Chen
- **URL:** https://devblogs.microsoft.com/oldnewthing/20261001-57/?p=112747

### 要約
Itanium の固定長命令バンドルでは、関数先頭の最初のバンドルを `nop` と 64 ビット長分岐 `brl.cond.sptk target64` に置き換えることでホットパッチを実現でき、AArch64 のような予備領域は不要でした。関数前に見えるブレークポイント命令のバンドルはホットパッチ用ではなく、関数開始位置を 32 バイト境界へ揃えるパディングです。

### 開発者にとって重要なこと
Itanium のバイナリ形式や Windows のホットパッチ機構を調査する開発者に、固定長バンドル、分岐レジスター、長分岐命令の制約を示す事例となります。現行の一般的な Windows/CPU を対象にした実装へ直接適用する内容ではありません。

### アクションプラン
- 低レベルツールや互換性調査を行う場合は、Itanium の命令バンドル構造と `brl` の分岐先要件を確認し、対象バイナリを逆アセンブルして検証する。
- 関数前の `break` バンドルをホットパッチ領域とみなさず、アラインメント用パディングかどうかを周辺の関数配置と併せて判定する。

- [Windows on Itanium also provided for hot-patching, in an even simpler way](https://devblogs.microsoft.com/oldnewthing/20261001-57/?p=112747)

## Advanced Shader Delivery Coming Soon across Windows 11 and Available for Gears of War: E-Day Today

- **Blog:** Directx
- **Author:** Wendy Ho
- **URL:** https://devblogs.microsoft.com/directx/advanced-shader-delivery-available-for-gears-of-war-e-day-and-coming-soon-across-windows-11

### 要約
Advanced Shader Delivery (ASD) の対応範囲が AMD RDNA に加えて Intel、NVIDIA、Qualcomm 搭載の Windows デバイスへ拡大し、Gears of War: E-Day が対応タイトルとして公開されました。ゲーム配布時にコンパイル済みシェーダーを提供することで、初回起動時のシェーダー処理を短縮し、実行時コンパイルに伴うスタッターを低減します。

### 開発者にとって重要なこと
PC ゲーム開発者は、起動時間とシェーダーコンパイル由来の体験を改善するため、ASD の state object database (SODB) と IHV コンパイラープラグインを利用する選択肢を得ました。Windows 11 24H2 以降、GPU 世代、ドライバーなどの要件があり、対応ハードウェアごとの検証が必要です。

### アクションプラン
- DirectX ゲーム開発チームは公式の D3D12 Advanced Shader Delivery サンプルで SODB の収集、ストアへのアップロード、対応ドライバーの構成を確認する。
- Windows 11 24H2 以降の AMD、Intel、NVIDIA、Qualcomm の対象 GPU とドライバーで、初回起動時間、シェーダーコンパイル、実行時スタッターを比較測定する。
- 対象タイトルを配布する場合は、GPU ベンダー別のサポート範囲と段階的なロールアウトを計画し、最新ドライバーを利用者へ案内する。

## GitHub-hosted agents with Pay-as-you-Go pricing are now generally available in Azure Pipelines

- **Blog:** DevOps
- **Author:** Eric van Wijk
- **URL:** https://devblogs.microsoft.com/devops/github-hosted-agents-with-pay-as-you-go-pricing-are-now-generally-available-in-azure-pipelines

### 要約
Azure Pipelines で GitHub-hosted agents と従量課金が一般提供され、macOS のエージェント SKU が GA、Linux と Windows の SKU がパブリック プレビューになりました。Apple silicon、より大きな Linux/Windows マシンなどを選べ、既存の並列ジョブ容量とは別に、選択した SKU の実行時間だけ支払います。

### 開発者にとって重要なこと
Apple 開発や大規模ビルドなど、特定のハードウェアを必要とする Azure Pipelines に適した実行環境を選べます。既存パイプラインは明示的に変更しない限り影響を受けませんが、無料枠がなく分単位で課金されるため、SKU 選択と利用量の監視が重要です。

### アクションプラン
- Azure DevOps 管理者は Billing で GitHub-hosted Agents を有効化し、プールのプロビジョニング完了後に対象パイプラインを限定して移行する。
- ビルド要件に応じて `xcode-27-xlarge`、`ubuntu-24.04-8-core`、`windows-2025-vs2026-16-core` などを選び、実行時間・成功率・キャッシュ・コストを既存エージェントと比較する。
- Analytics と Azure Cost Management で SKU、プロジェクト、パイプライン別の利用量を監視し、予算・アラートと上限運用を設定する。
- ⚠️ Ubuntu 26.04 と一部 Windows イメージは段階的ロールアウト中のため、利用可能性を組織単位で確認してからイメージを固定する。

## Migrating Elasticsearch Mappings to Azure Cosmos DB

- **Blog:** Cosmosdb
- **Author:** Madeline Egan
- **URL:** https://devblogs.microsoft.com/cosmosdb/migrating-elasticsearch-mappings-to-azure-cosmos-db

### 要約
Elasticsearch の mapping を Azure Cosmos DB へ移行する際は、スキーマを一対一で変換するのではなく、検索意図をインデックス ポリシー、フルテキスト ポリシー、ベクターポリシー、computed properties へ分配します。通常のフィルター・ソート・範囲検索、分析済み全文検索、ベクトル検索、導出値について対応する設定例と、代表データでの検証手順が示されています。

### 開発者にとって重要なこと
Elasticsearch 移行チームは、フィールドの型ではなく実際のクエリ用途を棚卸しし、Cosmos DB のコンテナー単位のポリシーへ再設計する必要があります。機能互換だけでなく、検索結果の正しさ、ランキング、レイテンシー、RU 消費、書き込みコストを比較しないと、移行後の性能や検索品質を判断できません。

### アクションプラン
- 検索チームは mapping、テンプレート、analyzer、ベクトル設定、runtime fields と、それらを使うクエリをエクスポートしてフィールドごとの用途を分類する。
- 通常の indexing policy、full-text policy/index、vector embedding policy/index、computed properties をまとめて設計し、パーティションキーと複合インデックスの要件も決める。
- 代表データと実クエリで結果の正しさ、関連度、レイテンシー、RU、書き込みコストを比較し、インデックス変換の完了とロールバック手段を確認して段階導入する。

### リファレンス
- [Migrating Elasticsearch Mappings to Azure Cosmos DB](https://devblogs.microsoft.com/cosmosdb/migrating-elasticsearch-mappings-to-azure-cosmos-db)
