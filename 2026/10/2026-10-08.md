## Dynamic Workflows in Azure Functions Hosted Skills: Durable, AI-Led Work for Event-Driven Apps

- **Blog:** Azure Sdk
- **Author:** Tsuyoshi Ushio
- **URL:** https://devblogs.microsoft.com/azure-sdk/dynamic-workflows-azure-functions-hosted-skills

### 要約
Azure Functions Hosted Skills の Dynamic Workflows は、LLM がタスクを依存関係付き DAG として計画し、Durable Functions がその実行を LLM の推論ループから分離して処理するプレビュー機能です。タスクの並列実行や結果の受け渡しに加え、Durable Functions による再試行・クラッシュ復旧・長時間待機と、Durable Task Scheduler の進捗確認を利用できます。

### 開発者にとって重要なこと
複数段階に及ぶイベント処理では、ツール実行ごとにLLMへ結果を戻す方式と比べ、トークン消費や推論待ちを抑えながら耐久性のある処理を構成できます。サブエージェントやツール内部でLLMを呼び出す場合は引き続きトークンと遅延が発生し、待機中にもバックエンド料金が発生し得ます。また、機能はプレビューで仕様変更の可能性があります。

### アクションプラン
- 複数ステップのイベント駆動処理がある場合は、ワークフローを DAG に分割できるか、並列化・再試行・長時間実行が必要かを整理する。
- 採用を検討する場合は `.agent.md` の `workflows.enabled: true` と公式サンプルを使い、依存関係・権限検証、失敗時の再試行、進捗確認をテストする。
- LLM 呼び出しを含むタスクと Durable Functions の待機を区別して、代表的な負荷で遅延・トークン使用量・バックエンド費用を測定する。
- ⚠️ プレビュー機能のため、本番導入前に変更可能性とサポート範囲を確認する。利用には Python 3.13 以降、Azure Functions Core Tools v4、ローカル実行時の Azurite、対応するモデルが必要。

## Adding persistence to the Aspire dashboard

- **Blog:** Aspire
- **Author:** James Newton-King
- **URL:** https://devblogs.microsoft.com/aspire/aspire-dashboard-persistence

### 要約
Aspire 13.6 のダッシュボードは SQLite にテレメトリを保存し、アプリを再起動した後も過去の実行履歴、リソース状態、ログ、トレース、メトリックを参照できるようになりました。既定のログ・トレース保存上限は各 10,000 件から 100,000 件に増え、記事のベンチマークでは大規模テレメトリ時のプライベートメモリ使用量が Aspire 13.5 の約 1,007 MB から 13.6 の約 241 MB に減少しています。

### 開発者にとって重要なこと
以前の実行時に起きた問題を再現せずに調査でき、開発中のテレメトリをより多く保持できます。保存データにはリソース構成やテレメトリ中の機密情報が含まれる可能性があり、スタンドアロン利用では既定の永続化モードが `None` のため、保持方法と保存先を明示的に選ぶ必要があります。

### アクションプラン
- AppHost 利用チームは Aspire CLI と AppHost パッケージを 13.6 に更新し、run selector から過去の実行データを確認する。
- スタンドアロン利用では用途に応じて `Run` または `Resume` を選び、コンテナー運用ではデータを保持するボリュームと保存先を設定する。
- 保存テレメトリに秘密情報が含まれないか確認し、ユーザープロファイル配下の保存先や `ASPIRE_HOME`、明示的なデータディレクトリのアクセス制御を点検する。
- 増加した既定テレメトリ上限が開発マシンのディスク使用量やチームの保持方針に合うか確認し、必要に応じて設定を調整する。

### リファレンス
- [Adding persistence to the Aspire dashboard](https://devblogs.microsoft.com/aspire/aspire-dashboard-persistence)

## New Wiki Editor Experience

- **Blog:** DevOps
- **Author:** Dan Hellem
- **URL:** https://devblogs.microsoft.com/devops/new-wiki-editor-experience

### 要約
Azure DevOps Wiki の既存エディターを、Visual Studio Code と同じ技術を使う Monaco Editor に置き換える新しい編集体験がプレビューとして発表されました。Markdown のシンタックスハイライトと行番号、検索・置換、改善された undo/redo、PR・ユーザー・work item・Wiki リンク・テンプレートの補完、折り返しや同期スクロールの設定保持に対応します。

### 開発者にとって重要なこと
Wiki を日常的に編集する開発者は、VS Code に近い操作や補完を利用でき、文章の更新やリンク挿入を効率化できます。機能はプレビューとして提供され、個人単位または組織全体で有効化できるため、利用範囲を選んで既存の編集手順との適合性を確認できます。

### アクションプラン
- Azure DevOps の **Preview features** から個人または組織向けに新エディターを有効化し、Wiki の編集・保存・補完を試す。
- Wiki を多用するチームは、検索・置換、貼り付け後の undo/redo、テンプレートやリンク補完が既存の作業手順に合うか評価する。
- プレビュー利用中に問題や改善要望があれば、記事のコメントまたは Developer Community からフィードバックを送る。

## If one anti-malware software is good, does that make two better?

- **Blog:** The Old New Thing
- **Author:** Raymond Chen
- **URL:** https://devblogs.microsoft.com/oldnewthing/20261008-00/?p=112762/

### 要約
複数のマルウェア対策ソフトが同じシステム関数を detour（フック）すると、一方が他方の処理を検知・隔離しようとし、互いの介入が複雑な障害を引き起こす場合があると説明しています。システム関数への介入は正式にサポートされない挙動を含むことがあり、問題の特定や製品同士の干渉回避が難しい点を指摘しています。

### 開発者にとって重要なこと
低レベルのシステム関数に介入するセキュリティ製品が複数共存すると、アプリケーション障害やハングの原因を追いにくくなることがあります。特に企業端末や検証環境で障害を調査する際、アプリの不具合だけでなく、インストール済みの保護製品間の干渉も切り分け対象になります。

### アクションプラン
- Windows 環境で原因不明の障害やハングを調査するときは、端末に導入されているマルウェア対策製品と、それらが同時稼働する構成を確認する。
- セキュリティ製品の干渉が疑われる場合は、組織のセキュリティ担当者・ベンダーと連携し、承認された検証環境でログや再現条件を調べる。
- 保護機能の無効化や製品削除を独断で行わず、複数製品を併用する必要性とサポートされる構成を管理者・ベンダーに確認する。

- [If one anti-malware software is good, does that make two better?](https://devblogs.microsoft.com/oldnewthing/20261008-00/?p=112762/)

## Pre-authenticated (tempauth) URLs are retiring: move to Microsoft Entra ID tokens before April 1, 2027

- **Blog:** Microsoft365dev
- **Author:** SharePoint team
- **URL:** https://devblogs.microsoft.com/microsoft365dev/pre-authenticated-tempauth-urls-are-retiring-move-to-microsoft-entra-id-tokens-before-april-1-2027

### 要約
2027 年 4 月 1 日から SharePoint Online と OneDrive は、Microsoft Graph の対象ファイル API が返す `tempauth` 付き事前認証 URL を段階的に廃止します。対象 URL の利用には Microsoft Entra ID のアクセストークンが必要になり、従来の 302 リダイレクトに依存する API はリダイレクトを返さずコンテンツを直接返す方式に変わります。対応 API では、テナント設定により Microsoft Graph URL を利用する選択肢も案内されています。

### 開発者にとって重要なこと
Graph の応答に含まれる `uploadUrl`、`getUrl`、ダウンロード URL、thumbnail や monitor URL などを認証ヘッダーなしで呼び出す実装は、移行が必要になる可能性があります。SharePoint Online URL を直接呼ぶ場合は SharePoint 用 audience（`https://{tenant}.sharepoint.com`）のトークンを使い、対応する Graph URL を使う場合は Graph 用トークンを使うなど、URL とトークンの audience を一致させる必要があります。

### アクションプラン
- Graph 応答から URL を取得して後続呼び出しする全箇所を検索し、`tempauth`、`@microsoft.graph.downloadUrl`、`uploadUrl`、`getUrl`、monitor URL、302 の `Location` への依存を洗い出す。
- リダイレクトを前提とした処理を見直し、返却 URL の種類に応じた Microsoft Entra ID トークンを Authorization ヘッダーに付けてアクセスする。可能な場合は `driveItem/contentStream` の利用も評価する。
- URL を永続的なアクセス手段として保存・転送・キューイングしないようにし、Graph と SharePoint Online の必要な権限・トークン audience をアプリ登録と実装で確認する。
- ⚠️ 2027 年 4 月 1 日より前にテストテナントで対象 API とテナント設定を検証し、顧客向けアプリでは十分な余裕をもって更新版を提供する。

## Faster by Design: Performance engineering in the Microsoft JDBC Driver for SQL Server

- **Blog:** Java
- **Author:** Ananya Garg
- **URL:** https://devblogs.microsoft.com/java/faster-by-design-performance-engineering-in-the-microsoft-jdbc-driver-for-sql-server

### 要約
Microsoft JDBC Driver for SQL Server の複数リリースにわたる性能改善として、ResultSet の NULL 判定や値のデコード、オブジェクト割り当て、文字列取得のホットパスを最適化し、バッチ挿入では Bulk Copy の設定項目と対応データ型を拡張した取り組みが紹介されています。さらに、パラメーター長の明示、Always Encrypted の鍵キャッシュ再利用、高並行認証時に有効なトークンをキャッシュから先に取得する最適化も説明されています。

### 開発者にとって重要なこと
SQL Server を利用する Java アプリでは、アプリケーションの使い方や処理結果を変えずに、ResultSet 読み取り、バッチ投入、暗号化、認証の負荷を軽減できる可能性があります。効果はデータ型、NULL の割合、バッチ構成、同時実行数などに依存するため、実際のワークロードで計測が必要です。記事では Spark の高スループット取り込みで `packetSize=32767` を評価する案も示されています。

### アクションプラン
- 使用中の Microsoft JDBC Driver を最新リリースと照らし合わせ、代表的な ResultSet・バッチ挿入・暗号化・高並行認証の負荷テストで性能と互換性を比較する。
- バッチ INSERT が対象なら `useBulkCopyForBatchInsert=true` と追加の Bulk Copy 接続プロパティを確認し、制約・トリガー・NULL・identity の扱いがアプリの要件に合うか検証する。
- パラメーターの型と長さが分かる場合は `defineParameterType()` または長さ指定付き `setObject()` を評価し、SQL Server の実行計画と追加メタデータ取得への影響を確認する。
- Spark の取り込みでは `packetSize=32767` を代表的なネットワーク・バッチ・パーティション構成で測定し、実環境で効果がある場合に限り採用する。

### リファレンス
- [Faster by Design: Performance engineering in the Microsoft JDBC Driver for SQL Server](https://devblogs.microsoft.com/java/faster-by-design-performance-engineering-in-the-microsoft-jdbc-driver-for-sql-server)
