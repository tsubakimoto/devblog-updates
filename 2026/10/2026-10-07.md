## Azure Document Intelligence と Azure Content Understanding の実践的な選び方

- **Blog:** Foundry
- **Author:** Chu Lahlou
- **URL:** https://devblogs.microsoft.com/foundry/choosing-azure-document-intelligence-and-content-understanding

### 要約
Azure Document Intelligence (ADI) と Azure Content Understanding (ACU) は OCR やレイアウト解析などの機能が重なる一方、ADI は安定した構造の帳票や学習済みの専用モデルに、ACU は多様・非構造化データ、推論、RAG、画像・音声・動画を含む処理に適しています。既存の ADI が要件を満たすなら移行は不要で、新規または拡張するワークロードを代表データで比較評価することを勧めています。

### 開発者にとって重要なこと
サービス選択は文書の種類だけでなく、項目が明記されているか推論が必要か、レイアウトのばらつき、ラベル付きデータの有無、品質・遅延・コスト、クラウドまたはコンテナーの要件で変わります。ACU の一部機能（高度な文脈化やエージェントモードなど）はプレビューであり、本番適用時には制約と評価結果の確認が必要です。

### アクションプラン
- 文書処理の新規・拡張案件では、構造、抽出項目、入力のばらつき、モダリティ、配置先、品質・遅延・コスト目標を整理する。
- ADI と ACU の両方が候補になる場合は、代表的な文書を用いて抽出精度、信頼度・根拠、処理時間、価格を同じ条件で比較する。
- 既存の ADI が本番要件を満たしている場合はそのまま運用し、現在の方式で扱いにくい非構造化データや RAG などに ACU を選択的に評価する。
- ⚠️ プレビュー機能を本番利用する場合は、サポート範囲と変更可能性を確認する。オンプレミスやエアギャップが必要な場合は ADI コンテナーの適合性も確認する。

### リファレンス
- [Azure Document Intelligence and Azure Content Understanding: a practical guide](https://devblogs.microsoft.com/foundry/choosing-azure-document-intelligence-and-content-understanding)

## Windows での AI 開発: PyTorch、llama.cpp から Windows ML まで

- **Blog:** Foundry On Windows
- **Author:** Anastasiya Tarnouskaya
- **URL:** https://devblogs.microsoft.com/foundry-on-windows/build-on-winml-oct-7-26

### 要約
Windows ML に実験的な llama.cpp/GGUF 対応が追加され、Text Generation API から GGUF と ONNX の言語モデルを扱えるほか、ONNX Whisper を使う Speech Recognition API も紹介されています。低レベル制御向けの Windows ML Runtime API はプレビューで、Windows Arm64 向け PyTorch、Windows 上の Triton、モデルの最適化・ビルド・計測を支援する Windows ML CLI など、ローカル AI 開発の選択肢も拡充されました。

### 開発者にとって重要なこと
Windows PC 上で GGUF や ONNX モデルをローカル実行し、テキスト生成や音声認識を組み合わせたアプリを試せます。高レベル API から始めて必要に応じ Runtime API に進める構成ですが、新しい Windows ML 経路は実験的で、GPU・CPU・NPU や Windows on Arm を含む実機環境での互換性・性能検証が欠かせません。

### アクションプラン
- Windows 上でローカル推論を検討しているチームは、対象モデル形式とデバイスに合わせて Text Generation API、Speech Recognition API、または OpenAI 互換ローカルエンドポイントを試す。
- 複数モデルの合成やデバイス配置を細かく制御する必要がある場合は、プレビューの Windows ML Runtime API とサンプルを確認する。
- PyTorch/Triton で開発・最適化したモデルを Windows ML CLI で解析、ビルド、ベンチマークし、対象端末で既存方式と品質・速度を比較する。
- ⚠️ 実験的な llama.cpp 統合と Runtime API は、本番採用前に対象デバイス、対応機能、既知の制限を確認する。

### リファレンス
- [AI Development on Windows: from PyTorch and llama.cpp to Windows ML](https://devblogs.microsoft.com/foundry-on-windows/build-on-winml-oct-7-26)

## Visual Studio Code 1.141

- **Blog:** VS Code Blog
- **Author:** Visual Studio Code Team
- **URL:** https://devblogs.microsoft.com/vscode-blog/visual-studio-code-1.141

### 要約
VS Code 1.141 では、Copilot harness と Agents ウィンドウのセッション管理が強化され、非アクティブなエージェント用 worktree の確認・整理、バックグラウンドシェルの監視、セッションの絞り込みなどが追加されました。エージェントホストのサンドボックス設定、複数の GitHub Enterprise インスタンスへのサインイン、エージェントのセッションをまたぐ操作、エディターの複数行ペーストなども更新されています。

### 開発者にとって重要なこと
エージェントを並行利用する開発者は、進行中のコマンドやセッションを追跡しやすくなり、不要な worktree によるディスク使用量を管理できます。サンドボックスはファイル・ネットワークアクセスを制限する追加防御ですが、単独のセキュリティ境界ではありません。企業環境では、旧 `github-enterprise.uri` 設定の非推奨化や、サンドボックスを必須化する管理設定への移行も関係します。

### アクションプラン
- VS Code を 1.141 に更新し、エージェントを利用する場合は Copilot harness、バックグラウンドシェル表示、worktree クリーンアップを実際の運用に合わせて試す。
- ローカルおよびリモートのエージェント実行では `chat.agent.sandbox.enabled` と権限設定を確認し、必要に応じて OS・ネットワーク制約を検証する。
- 複数の GHE.com / GHES を使う場合は `github-enterprise.uris` に移行し、利用する GitHub 拡張機能ごとの複数インスタンス対応範囲を確認する。
- 管理者は旧サンドボックスポリシーの扱いを確認し、サンドボックスを必須化する場合は統合管理設定の `sandbox.enabled` と `sandbox.allowBypass` を検討する。

### リファレンス
- [Visual Studio Code 1.141](https://devblogs.microsoft.com/vscode-blog/visual-studio-code-1.141)

## Spec-First からエンタープライズ対応へ: GitHub Spec Kit の拡張

- **Blog:** Blog
- **Author:** Apoorv Gupta
- **URL:** https://devblogs.microsoft.com/blog/from-spec-first-to-enterprise-ready-extending-github-spec-kit

### 要約
GitHub Spec Kit を組織規模で利用するため、コアをフォークせずに開発標準やドメイン要件を反映する拡張モデルを解説しています。既存動作を調整する presets、新機能を加える extensions、それらを配布する bundles、手順やレビューを組み立てる workflows に加え、承認済み組織カタログとコミュニティカタログを分けるガバナンスを提案しています。

### 開発者にとって重要なこと
仕様駆動開発のテンプレート・ルールや AI エージェント向けガードレールを、組織・ドメイン・チームの各層で共有できます。一方、カタログ掲載はコードの安全性や組織の承認を保証しないため、配布元、所有者、プロンプト、スクリプト、更新方法を確認する運用が重要です。

### アクションプラン
- チームの Spec Kit 活用を始める場合は、適用すべき組織標準とプロジェクト固有の裁量範囲を整理する。
- 既存テンプレートや用語の調整には presets、新しい検査・連携機能には extensions を使い、個別に文書化・バージョン管理・テストする。
- カタログに登録する前に、所有者・ソース・権限・プロンプト・スクリプト・更新方針をレビューし、承認済みの組織カタログを整備する。
- 検証済みの preset と extension の組み合わせを bundles 化し、手順と人による承認点が明確になってから workflows で自動化する。

### リファレンス
- [From Spec-First to Enterprise-Ready: Extending GitHub Spec Kit](https://devblogs.microsoft.com/blog/from-spec-first-to-enterprise-ready-extending-github-spec-kit)

## 未定義の opcodes `ud0` と `ud1` にパラメーターがあるのはなぜか？

- **Blog:** Oldnewthing
- **Author:** Raymond Chen
- **URL:** https://devblogs.microsoft.com/oldnewthing/20261007-00/?p=112759

### 要約
`ud0` / `ud1` がオペランドを持つのは、命令として意味が定義されていないことと、命令デコーダーがそのバイト列をどのように解析するかが別だからだと説明しています。未割り当てだった `0F FB` と `0F FF` は既存 CPU で不正命令として使われていたため、後に `PSUBQ` / `PADDQ` を追加する際、互換性を保つため `PADDQ` は別の opcode (`0F D4`) に置かれました。

### 開発者にとって重要なこと
プロセッサの「未定義」命令でもデコーダーがオペランドを解析する場合があり、後方互換性が命令セット拡張の設計を制約する例です。アセンブラーやバイナリの調査では、命令の表記だけでなくエンコード、世代ごとの仕様、実際の互換挙動を区別する必要があります。

### アクションプラン
- x86 命令のデコードやアセンブラー出力を扱う場合は、対象 CPU 世代の命令セット資料と opcode 表を確認する。
- 未定義・非公式 opcode の挙動に依存するコードを作らず、必要に応じて対象ハードウェアで互換性を検証する。
- 命令デコーダーや逆アセンブラーを実装する場合は、不正命令判定だけでなく、デコード済みオペランドと例外発生位置もテストする。
