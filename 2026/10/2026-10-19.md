## Go 1.27.2-2 Microsoft build now available

- **Blog:** Go
- **Author:** George Adams
- **URL:** https://devblogs.microsoft.com/go/go-1-27-2-2-microsoft-build-now-available

### 要約
Microsoft Build of Go 1.27.2-2 が公開されました。Microsoft 固有の変更として、TLS の `signature_algorithms_cert` で ML-DSA 証明書署名の通知を省略できる `ms_tlsmldsacert` GODEBUG 設定と、`go env -w` やインストール先の `go.env` を通じてテレメトリ設定を永続化する機能が追加されています。上流の Go 1.27.2 をベースにしています。

### 開発者にとって重要なこと
TLS インスペクション機器が ML-DSA の通知を正しく処理できず接続を切断する環境では、設定による回避策を選べます。設定の既定値は `1` で、上流と同じ通知動作を維持します。テレメトリは既定で有効なため、利用者や配布元の方針に応じた設定が必要です。

### アクションプラン
- Microsoft Build of Go の利用者は、1.27.2-2 の変更と上流の Go 1.27.2 リリースノートを確認し、更新対象の開発環境・ビルド環境に適用する。
- TLS 接続が非準拠の中間機器でリセットされる場合に限り、`ms_tlsmldsacert=0` を検証する。ML-DSA 暗号スイート自体を無効化する設定ではない点に留意する。
- 配布環境でテレメトリを無効にする必要がある場合は、公式ドキュメントに従って `go.env` などで設定し、チーム・組織の方針と整合させる。

## Get Your .NET MAUI App Ready for Xcode 27

- **Blog:** .NET
- **Author:** Gerald Versluis
- **URL:** https://devblogs.microsoft.com/dotnet/migrate-dotnet-maui-apps-uikit-scene-lifecycle

### 要約
Xcode 27 でビルドした既存の .NET MAUI アプリが iOS 27 で起動直後に終了し、「UIScene life cycle is required for apps built with this SDK」と記録される場合、UIKit の scene lifecycle への移行が必要です。基本的な対応は scene delegate と `UIApplicationSceneManifest` の追加ですが、独自の認証コールバック、ディープリンク、App Actions などは scene 側のイベントへ適切に移す必要があります。記事では、プロジェクトを調査・移行・検証する実験的な MAUI CLI エージェントスキルも紹介しています。

### 開発者にとって重要なこと
MAUI や workload を更新しただけでは既存プロジェクトの iOS 設定は書き換わらず、従来の application lifecycle のままでは Xcode 27 で問題が起きる可能性があります。記事執筆時点の .NET 10 向け iOS / Mac Catalyst workload 27.0.10722 は Xcode 27.0 を必要とし、.NET MAUI 10.0.110 以降では App Actions と `WebAuthenticator` の scene 対応も含まれます。SDK の最低 OS 要件も iOS 15、Mac Catalyst 17 となるため、古い OS のサポートを維持するアプリは移行計画が必要です。

### アクションプラン
- iOS アプリのチームは `maui doctor` などで .NET SDK、MAUI workload、Xcode の互換性を確認し、Xcode 27 を使う場合は scene delegate と manifest が既に存在するか調べる。
- 移行する場合は `AppDelegate` の独自ライフサイクル処理、認証、起動時・実行中のディープリンク、通知タップ、App Actions を確認し、scene イベント側に移して実機で検証する。Debug / Release など複数の plist と Mac Catalyst の設定も確認する。
- iOS 15 未満や Mac Catalyst 17 未満のサポートが必要なら、SDK 更新でサポート対象を暗黙に切り捨てず、互換 SDK の利用を含めてチームで方針を決める。
- 移行スキルを使う場合は、必要な MAUI CLI がプレビュー版でサポート対象外であることを踏まえ、変更差分を確認してから採用する。

### リファレンス
- [Get Your .NET MAUI App Ready for Xcode 27](https://devblogs.microsoft.com/dotnet/migrate-dotnet-maui-apps-uikit-scene-lifecycle)

## Bring Your Own Model to the GitHub Copilot SDK with C#

- **Blog:** .NET
- **Author:** Bruno Capuano
- **URL:** https://devblogs.microsoft.com/dotnet/bring-your-own-model-to-the-github-copilot-sdk-with-csharp

### 要約
GitHub Copilot SDK のエージェントランタイムを使いながら、`ProviderConfig` で推論先を独自のモデルプロバイダーにする C# サンプルが公開されました。例では .NET 10 アプリから Microsoft Foundry または Azure OpenAI の OpenAI Responses API 互換デプロイメントへ接続し、Azure CLI を使う Microsoft Entra ID 認証、または API キー認証を選べます。Copilot SDK が提供するランタイムと、モデル推論を行うプロバイダーは別々に構成します。

### 開発者にとって重要なこと
既存のエージェントランタイムを維持しつつ、モデルの接続先や認証を自分たちで管理できる構成例です。サンプルではツールなどを無効にして BYOK 接続に焦点を絞っており、任意のモデルや API がそのまま互換になるとは限りません。Responses API 対応、認証方式、トークン上限を対象デプロイメントに合わせて確認する必要があります。

### アクションプラン
- Copilot SDK を C# アプリで使うチームは、サンプルを参照し、利用するモデルデプロイメントが Responses API に対応しているか確認する。
- Foundry / Azure OpenAI 接続では、エンドポイントとデプロイ名を構成し、Entra ID を使う場合は `az login` と Cognitive Services OpenAI User ロールを確認する。API キーはソースに含めず、User Secrets など適切なシークレット管理に置く。
- 推論モデルを使う場合は、出力トークン上限に reasoning tokens も含まれることを踏まえ、サンプル値をそのまま流用せず応答の打ち切りやコストを検証する。

### リファレンス
- [Bring Your Own Model to the GitHub Copilot SDK with C#](https://devblogs.microsoft.com/dotnet/bring-your-own-model-to-the-github-copilot-sdk-with-csharp)

## Plan Your Java Upgrade Ahead of Microsoft's 2027 Support Milestones

- **Blog:** Java
- **Author:** Bruno Borges
- **URL:** https://devblogs.microsoft.com/java/plan-your-java-upgrade-ahead-of-microsofts-2027-support-milestones

### 要約
Microsoft Build of OpenJDK のサポートロードマップでは、Java 11 と 17 のサポート終了が 2027 年 9 月以降の初期目標として示されており、Azure App Service と Functions では Java 8、11、17 のサポートが 2027 年 9 月 1 日に終了する予定です。記事は Java 21 または 25 への移行に向け、Modernize CLI で評価・計画を行い、テストと段階的なロールアウトを含むレビュー可能な変更にする方法を説明しています。

### 開発者にとって重要なこと
サポート期限は JDK ディストリビューション全体、Azure のマネージドサービス、他ベンダーの方針で異なります。Microsoft Build of OpenJDK のロードマップでは Java 21 は 2028 年 9 月、Java 25 は 2030 年 9 月が初期の終了目標です。期限後もアプリが動き続ける場合がありますが、対象ランタイムではセキュリティ更新や関連サポートが受けられなくなるため、CI と本番環境を含む移行計画が必要です。

### アクションプラン
- Java 8 / 11 / 17 を使うチームは、まず実行環境ごとのバージョン、JDK の配布元、Azure サービスのサポート期限を棚卸しし、適用されるポリシーを確認する。
- Modernize CLI などで依存関係、フレームワーク、ビルドツールを評価し、Java 21 などの移行先と必要な変更を明確にした計画をレビューしてから実行する。
- CI の JDK、Maven / Gradle 設定、コンテナイメージ、Azure のランタイムを揃え、単体・統合テストに加えてステージング環境で API、DB 接続、監視エージェント、性能を確認し、ロールバック手順を用意する。
- フレームワーク移行など必須ではない変更を互換性対応と分離し、移行の範囲とレビュー根拠をプルリクエストに記録する。

### リファレンス
- [Plan Your Java Upgrade Ahead of Microsoft's 2027 Support Milestones](https://devblogs.microsoft.com/java/plan-your-java-upgrade-ahead-of-microsofts-2027-support-milestones)

## Organize and revisit tabs with the keyboard

- **Blog:** Visual Studio
- **Author:** Mads Kristensen
- **URL:** https://devblogs.microsoft.com/visualstudio/organize-and-revisit-tabs-with-the-keyboard

### 要約
Visual Studio 2026 version 18.11 で、開いているタブの並び替えと位置指定での移動をキーボードから行えるようになりました。`Ctrl+Shift+PgUp` / `Ctrl+Shift+PgDn` でアクティブなタブを左右に移動し、`Ctrl+NumPad1`～`Ctrl+NumPad9` でアクティブなドキュメントグループ内の表示位置にあるタブを開けます。ツールウィンドウのタブ幅など、タブ表示の改善も含まれています。

### 開発者にとって重要なこと
実装・テスト・インターフェースを並べて作業する際、マウスを使わずタブ順を整え、位置で戻れるようになります。番号キーはファイル名に固定されず、表示順に従います。また、新しい移動ショートカットは Text Editor の `Edit.ViewTopExtend` / `Edit.ViewBottomExtend` の割り当てを置き換えるため、既存のキー操作に影響する場合があります。

### アクションプラン
- Visual Studio 2026 18.11 を利用する場合は、実装とテストなど少数のタブを並べて、新しい移動・位置指定ショートカットを試す。
- 既存のキーバインドと競合する場合は **Tools > Options > Environment > Keyboard** で `Window.MoveTabLeft` / `Window.MoveTabRight` や既存コマンドの割り当てを確認・調整する。
- タブの固定状態、縦タブのプロジェクトグループ、プレビュータブなどによって操作対象が制約される点をチーム内で共有する。

## Why do we need `ud2` when `int 6` is right there?

- **Blog:** Oldnewthing
- **Author:** Raymond Chen
- **URL:** https://devblogs.microsoft.com/oldnewthing/20261019-00/?p=112781

### 要約
x86 の未定義命令 `ud2` の代わりに `int 6` を使えない理由を、例外の意味の違いから解説しています。未定義命令は fault で、例外ハンドラーには問題の命令そのもののアドレスが通知されます。一方 `int 6` は trap で、次の命令のアドレスが通知されるため、OS の未定義命令ハンドラーが命令を調査する際に整合しません。

### 開発者にとって重要なこと
CPU 例外や低レベルのエラー処理では、fault と trap の違いが命令ポインターや再実行の挙動に影響します。また、保護モードではユーザーモードから `int 6` を発行する権限も通常認められておらず、ソフトウェア割り込みで未定義命令 fault を模倣することはできません。

### アクションプラン
- x86 の例外ハンドラーや命令エミュレーションを実装する場合は、fault と trap のどちらかで例外時の命令アドレスが変わることを考慮する。
- 未定義命令 fault を発生させる必要があるコードでは、`int 6` に置き換えず、対象 CPU と実行環境で有効な未定義命令を使用する。
- 関連する低レベルコードのレビューでは、例外後に命令を再実行するか次へ進むか、ハンドラーが参照する命令ポインターが正しいか確認する。

## Browser automation tool in Microsoft Foundry is now GA

- **Blog:** Foundry
- **Author:** Nandini Muralidharan
- **URL:** https://devblogs.microsoft.com/foundry/browser-automation-tool-ga

### 要約
Microsoft Foundry の Browser Automation Tool が一般提供になりました。Playwright Workspaces が管理するクラウドブラウザーを使い、エージェントは Web ページの確認、フォーム入力、複数段階の操作を実行できます。Prompt agents、Hosted agents、GitHub Copilot harness から利用でき、Toolboxes を通じて MCP 対応ツールとして再利用できます。

### 開発者にとって重要なこと
API がない社内ポータルや管理画面も、エージェントのワークフローに組み込めます。Playwright Workspace は別途 Azure リソースとして構成し、プライベートサイトにはプロビジョニング時の仮想ネットワーク接続が必要です。ブラウザー操作は実システムに影響しうるため、権限、承認、分離、監視を設計に組み込む必要があります。

### アクションプラン
- Foundry を使うチームは Playwright Workspace を用意し、Browser Automation Tool を Toolbox に接続して対象エージェントから利用できるか試す。
- 社内サイトを扱う場合は、ネットワーク接続と Entra ID / Azure RBAC の最小権限を確認し、まず閲覧など読み取り中心の操作から検証する。
- クリック、入力、送信など状態を変更する操作には必要に応じて承認を設け、Live View / Take control、ツール許可リスト、個別の分離セッションを活用する。
- Web ページ内容を信頼できない入力として扱い、遷移先や重要操作を検証する。Foundry traces に機微情報が含まれる可能性を考慮し、アクセス制御も確認する。

### リファレンス
- [Browser automation tool in Microsoft Foundry is now GA](https://devblogs.microsoft.com/foundry/browser-automation-tool-ga)
