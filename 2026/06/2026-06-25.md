## The case of the DLL that was not present in memory despite not being formally unloaded, part 1

- **Blog:** Oldnewthing
- **Author:** Raymond Chen
- **URL:** https://devblogs.microsoft.com/oldnewthing/20260625-00/?p=112467

### 要約
DLL が正式には unload されていないのにメモリ上に存在しない、というクラッシュ解析の話です。再帰的な例外処理や、強制的にメモリから外された DLL が原因で shell32 が被害者として見えている状況を掘り下げています。

### 開発者にとって重要なこと
Windows のクラッシュ解析、DLL のライフサイクル、COM/例外処理、メモリ破損の切り分けに関係します。似た症状のクラッシュを調べるチームや、低レベルの診断を行う開発者に有用です。

### アクションプラン
- 似たクラッシュがある場合は、`FreeLibrary` ではなく不正なメモリ解放や破損で DLL が外れていないか確認する。
- 再帰的な例外処理や stack overflow の痕跡を追い、最初の例外と被害 DLL を分けて見る。
- ⚠️ DLL の強制アンロードや不正なメモリ操作が疑われるなら、所有権と解放経路を重点的に監査する。

## Which Azure Cosmos DB Role Does My App Need?

- **Blog:** Cosmosdb
- **Author:** Sudhanshu Khera
- **URL:** https://devblogs.microsoft.com/cosmosdb/which-azure-cosmos-db-role-does-my-app-need

### 要約
Cosmos DB にアプリを接続するとき、どのロールを使い、どのスコープに割り当てるべきかを整理した投稿です。キーではなく managed identity と data plane RBAC を使う考え方を説明し、`DefaultAzureCredential` を使った接続例も示しています。

### 開発者にとって重要なこと
Cosmos DB を使うアプリの認証・認可設計に直接関係します。秘密情報を減らしたいチーム、Azure 上のアプリ、セキュリティレビューを通す必要があるプロジェクトに特に重要です。

### アクションプラン
- Cosmos DB へのアクセスを key ベースから managed identity + `DefaultAzureCredential` へ切り替える。
- 必要最小限の data role を選ぶ: 読み取りだけなら Data Reader、書き込みが必要なら Data Contributor。
- まずはアカウント全体スコープで始め、必要に応じて database/container へ絞る。
- ⚠️ 既存の接続文字列やキーがある場合は、移行後に削除して secret を残さない。
