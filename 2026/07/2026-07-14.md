## CoreCLR Progress and the Mono Timeline for .NET MAUI

- **Blog:** .NET
- **Author:** David Ortinau
- **URL:** https://devblogs.microsoft.com/dotnet/coreclr-progress-and-mono-timeline-dotnet-maui

### 要約
.NET MAUI のモバイルアプリで、.NET 11 Preview 6 から CoreCLR が唯一のランタイムになったことが案内されています。Mono のモバイル向け選択肢はなくなり、Android / iOS / Mac Catalyst はすべて CoreCLR に移行しました。

性能面では iOS と Mac Catalyst が Mono より概ね高速、Android は起動時間とアプリサイズで Mono にかなり近い状態だと説明されています。あわせて、Debugging、Hot Reload、オンデバイス診断、NativeAOT の基盤も進んでいるとしています。

### 開発者にとって重要なこと
.NET MAUI のモバイル開発者には直接影響があります。ランタイム移行の互換性、起動性能、Hot Reload、サードパーティ製ライブラリの挙動を実アプリで確認する必要があります。

### アクションプラン
- .NET 11 Preview 6 SDK と MAUI workload を入れて、実アプリをビルドして確認する。
- Android / iOS / Mac Catalyst で起動時間、サイズ、主要フロー、Hot Reload を .NET 10 と比較する。
- 反射や動的コード生成を使うライブラリを重点確認し、問題があればフィードバックする。

### リファレンス
- [CoreCLR Progress and the Mono Timeline for .NET MAUI](https://devblogs.microsoft.com/dotnet/coreclr-progress-and-mono-timeline-dotnet-maui)

## Package Status

- **Blog:** Insidemsix
- **Author:** Howard Kapustein
- **URL:** https://devblogs.microsoft.com/insidemsix/package-status

### 要約
Windows の package status フラグについて説明する投稿です。Package.Status で、パッケージが健全か、依存関係に問題があるか、無効化されているか、移動媒体のオフライン状態か、更新/修復中かを確認できます。

Tampered、Modified、DependencyIssue、PackageOffline、Disabled、DeploymentInProgress などの状態が整理され、起動前に Windows がどう判定するかも説明されています。Get-AppxPackage の Status 出力例も示されています。

### 開発者にとって重要なこと
Windows アプリやパッケージの配布・診断を扱う開発者、運用担当者、管理者に重要です。起動失敗や利用不可の原因を状態フラグで切り分ける必要があります。

### アクションプラン
- `PackageStatus.VerifyIsOK()` と個別フラグで、起動阻害の原因を確認する。
- `Get-AppxPackage` の Status を使って、配布や修復の問題を切り分ける。
- Tampered / Modified / Offline / Servicing の各ケースで、対応手順を用意する。

### リファレンス
- [Package Status](https://devblogs.microsoft.com/insidemsix/package-status)

## Microspeak: Double-click and drill down

- **Blog:** Oldnewthing
- **Author:** Raymond Chen
- **URL:** https://devblogs.microsoft.com/oldnewthing/20260714-00/?p=112532

### 要約
Microsoft 内部や技術文書で使われる言い回しとしての「drill down」と、最近見かける「double-click」というジャーゴンの使われ方を扱っています。著者は、後者は意味としては drill down に近いが、やや気取った言い回しだとしています。

Microsoft Writing Style Guide での「drill down / drill up / drill through」の扱いも紹介され、データ分析の文脈以外での比喩的使用は避けるべきだと整理されています。

### 開発者にとって重要なこと
ドキュメント、プレゼン、UI 文言を書く人に関係します。用語の選び方が読みやすさと一貫性に直結するため、社内外の文章で誤解の少ない表現を選ぶ必要があります。

### アクションプラン
- 「double-click」を深掘りの意味で使っていないか、ドキュメントと説明資料を見直す。
- データ分析なら「drill down / up / through」をスタイルガイドに沿って使う。
- 比喩表現よりも、何を確認するのかを具体的に書く。

### リファレンス
- [Microspeak: Double-click and drill down](https://devblogs.microsoft.com/oldnewthing/20260714-00/?p=112532)

## How a Large Enterprise Migrated 47 TB and 7,000+ Collections to Azure DocumentDB in Under 48 Hours

- **Blog:** Documentdb
- **Author:** Sandeep S. Nair
- **URL:** https://devblogs.microsoft.com/documentdb/migration-47tb-under-48-hours

### 要約
47 TB、7,000+ collections、27 ノード構成の MongoDB 互換環境を、48 時間未満で Azure DocumentDB に移行した事例です。移行を「通常運用」ではなく「移行専用のアーキテクチャ」として扱い、段階的に進めた点が強調されています。

Assessment-first、bulk ingestion 中の HA / cross-region replica / non-unique index の後回し、ソース構成をそのままコピーしないターゲット設計、4 つのバランスしたジョブ分割が成功要因として挙げられています。

### 開発者にとって重要なこと
大規模な DocumentDB / MongoDB 互換移行を計画するチームに直接役立ちます。データ移行では、性能最適化の順番と運用の可観測性が、単純なコピー以上に重要だと分かります。

### アクションプラン
- まず移行対象の collection を棚卸しし、不要データを除外する。
- bulk load 中は HA や index build を後回しにできないか検討する。
- ターゲットはソースの複製ではなく、実際の workload に合わせて設計する。

### リファレンス
- [How a Large Enterprise Migrated 47 TB and 7,000+ Collections to Azure DocumentDB in Under 48 Hours](https://devblogs.microsoft.com/documentdb/migration-47tb-under-48-hours)
