## T-SQL Hygiene: What's the Big Deal with SET NOCOUNT ON?

- **Blog:** Azure SQL
- **Author:** Jerry Nixon
- **URL:** https://devblogs.microsoft.com/azure-sql/tsql-nocount

### 要約
`SET NOCOUNT ON` が、ストアドプロシージャ内で「(x rows affected)」の余計なメッセージを抑止する理由を解説しています。`.NET` や Entity Framework では不要になりやすい通信と処理を減らせる一方、`ExecuteNonQuery()` では戻り値の扱いに注意が必要だとしています。

トランザクションや `SELECT`、`@@ROWCOUNT` 自体には影響せず、あくまで affected-row メッセージだけを抑える点が強調されています。

### 開発者にとって重要なこと
Azure SQL / SQL Server を使うアプリでは、ストアドプロシージャの挙動とクライアント側の期待値に直結します。特に更新件数を暗黙に頼っているコードや、複数ステップのプロシージャでは影響確認が必要です。

### アクションプラン
- ストアドプロシージャに `SET NOCOUNT ON` を入れる方針を見直す。
- `ExecuteNonQuery()` で件数に依存している箇所があれば、`@@ROWCOUNT` を明示返却する。
- 既存の SQL 呼び出しを、件数メッセージ前提で壊れないか確認する。

### リファレンス
- [T-SQL Hygiene: What's the Big Deal with SET NOCOUNT ON?](https://devblogs.microsoft.com/azure-sql/tsql-nocount)

## Announcing .NET Modernization for Beginners

- **Blog:** .NET
- **Author:** Pablo Lopes
- **URL:** https://devblogs.microsoft.com/dotnet/announcing-dotnet-modernization-for-beginners

### 要約
レガシーな .NET Framework アプリを .NET 10 まで近代化するための無料のハンズオンコースを紹介しています。GitHub Copilot modernization tooling を使い、`assessment.md`、`plan.md`、`tasks.md` の成果物をレビューしながら進める構成です。

コースは Assessment / Planning / Upgrade & Execution / Cloud with Azure の 4 章で、単なる自動変換ではなく、レビュー可能な計画を起点に進める点が特徴です。

### 開発者にとって重要なこと
旧 .NET アプリを抱えるチーム、移行計画を立てるアーキテクト、Copilot を使った近代化に興味がある開発者に関係します。手順化された移行プロセスを学べるので、移行の見積もりと実行の精度を上げやすくなります。

### アクションプラン
- 既存の .NET Framework アプリがあるなら、このコースで評価・計画の流れを試す。
- `assessment.md` と `plan.md` をチームでレビューし、移行方針を合意する。
- ⚠️ Copilot modernization を使う前提として、対象リポジトリの依存関係と運用制約を整理する。

## How to build long-running MCP tools on Azure Functions

- **Blog:** Azure Sdk
- **Author:** Lily Ma
- **URL:** https://devblogs.microsoft.com/azure-sdk/long-running-mcp-tools-azure-functions

### 要約
Azure Functions の MCP 拡張で、長時間かかるツールをどう扱うかを Durable Functions で実装する方法を紹介しています。MCP の Tasks extension は長時間実行を扱う標準化された仕組みですが、対応クライアントと SDK はまだ発展途上です。

現状の request/response 型の制約、`workflow_id` を使ったサンプル設計、`poll_after_seconds` による再試行誘導など、長時間ワークフローの実装パターンが説明されています。

### 開発者にとって重要なこと
Azure Functions で MCP サーバーや長時間処理ツールを作る開発者に関係します。クライアントのタイムアウトを前提に、同期応答だけでなくジョブ管理や状態参照の設計が必要になります。

### アクションプラン
- 長時間処理は Durable Functions で切り出し、即時応答と状態取得を分ける。
- `workflow_id` と `not_found` を含むポーリング設計を実装し、誤った再取得を防ぐ。
- ⚠️ 対応クライアントが Tasks extension をサポートしているか確認してから移行する。

### リファレンス
- [How to build long-running MCP tools on Azure Functions](https://devblogs.microsoft.com/azure-sdk/long-running-mcp-tools-azure-functions)

## Speculating on how the buggy control panel extension truncated a value that it had right in front of it

- **Blog:** Oldnewthing
- **Author:** Raymond Chen
- **URL:** https://devblogs.microsoft.com/oldnewthing/20260716-00/?p=112539

### 要約
64-bit 化した Windows コードで、`GWL_WNDPROC` を `GWLP_WNDPROC` に直したのに、キャストを `(LONG)` のまま残したためにポインタが切り詰められた、という推測を扱っています。見た目は直っていても、64-bit に必要な型更新が抜けるとバグが残ることを示しています。

`SetWindowLong` / `SetWindowLongPtr` の違い、`LONG_PTR` を使うべき理由、そして build break が「見落としを教える警告」だった点が説明されています。

### 開発者にとって重要なこと
Windows のネイティブコードや古い 32-bit 前提のコードを保守している開発者に重要です。移植時は API 名だけでなく、関連する型やキャストまで一緒に見直す必要があります。

### アクションプラン
- 64-bit 対応済みと思っている Win32 コードでも、`LONG` / `LONG_PTR` の取り違えを再確認する。
- `SetWindowLong` 系の置換では、API 名・引数型・戻り値型をセットで見直す。
- ⚠️ ポインタを整数に落としている箇所があれば、移植漏れとして重点的に点検する。
